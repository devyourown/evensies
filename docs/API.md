# Evensies API and sync contract

The contract shared by the server (Spring Boot) and the app (Flutter). Both implementations follow this document. To change something, change this document first.

## Common rules
- All IDs are UUID strings (generated by the app). Ids in event payloads are accepted only in lowercase canonical form (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`, the same value as `UUID.toString()`). Uppercase or short forms like `1-1-1-1-1` get 400 `VALIDATION` (state is looked up by the string and tables by the parsed UUID, so another spelling could overwrite the same row as if it were a different entity). Amounts are integers (minor units, `shared/currencies.json`; from phase 4, 155 ISO 4217 currencies, see "Currency conversion"). Dates are `YYYY-MM-DD`, times are ISO-8601 UTC.
- JSON keys are camelCase. Nullable fields are sent explicitly as `null`.
- Auth: `Authorization: Bearer <access>`. Not authenticated → 401. Not a group member → 403. Not found → 404.
- Error body: `{"code": "SUM_MISMATCH", "message": "..."}`. Validation errors are 400.

```
UserDto {"id","displayName","homeCurrency": string|null,"language": string|null,"email": string|null,"emailBounced": bool}
ServerInfo {"appleServicesId": string|null, "googleWebClientId": string|null, "devLogin": bool, "emailLogin": bool, "appleLogin": bool, "googleLogin": bool, "supportEmail": string|null, "reviewLogin": bool}
```
- `homeCurrency` (phase 4): the user's display currency ("≈ $13.46"). It is `null` if never saved, and the app then uses the device region's currency (`Money.currencyForLocale`). The sign-in response's `user`, `GET /me` and `PATCH /me` all return the same `UserDto`. The app reads a response without the key (older server) as `null`.
- Refresh (phase 5): when the app starts with a saved session and each time it comes back to the foreground (resume, together with `syncAll`), it calls `GET /me` and overwrites the session with the received `displayName` and `homeCurrency`. A name or home currency changed on another phone shows up without signing in again. If offline, 5xx or 429, the saved values stay. 401 works as now (sign out if the token refresh fails). Right after sign-in, the app uses the sign-in response's `user`. If the received `displayName` is an empty string, the app shows the name entry screen (above).
- `language` (phase 9, "Languages and web"): the language of text the server makes for this user (push, reminders, phase 10 emails). `null` = never set = English. The sign-in response's `user`, `GET /me` and `PATCH /me` all return the same `UserDto`. The app reads a response without the key (older server) as `null`. The UI language comes from the device language (or Settings → Language), not from this value (see "App language" below).
- `PATCH /me` checks (all checks run first, then everything is saved at once): `displayName` and `homeCurrency` count as absent when `null`. Only `language` differs: a missing key leaves it as is, `null` clears it (English), and a string must match `^[a-z]{2,3}$` (uppercase, regions `de_AT` and `de-AT`, one letter, `deutsch` and `<b>` get 400 `VALIDATION`). Any other JSON type gets 400 `VALIDATION`. A well-formed language that is not in `strings.json` (`xx`) is still saved, and text is made in English. If all three keys are absent (including `{}` and `{"displayName": null}`; `{"language": null}` has the key, so it clears), 400 `VALIDATION`. If `displayName` is out of range, 400 `VALIDATION`. If `homeCurrency` is not a string, 400 `VALIDATION`; a code not in the list (including `"usd"`) gets 400 `UNKNOWN_CURRENCY`. The home currency cannot be cleared (only changed). The old body `{"displayName"}` still works. The app sends it only when online (no offline queue). A deleted account gets 401 (same as now).

- `GET /info` (phase 9): `appleServicesId` = `EVENSIES_APPLE_SERVICES_ID`, `googleWebClientId` = `EVENSIES_GOOGLE_WEB_CLIENT_ID` (`null` if empty), `devLogin` = `evensies.auth.dev-login`. No rate limit. The web uses the two ids; phones use the ids built into the build but read the rest (which buttons to show) too. Phase 10: `emailLogin`, `appleLogin`, `googleLogin` and `supportEmail` (see "Email and account" below). `email` and `emailBounced` (`UserDto`, phase 10) are described there too.
- Accepted `aud` (phase 9): for `/auth/apple`, the non-empty values among {`EVENSIES_APPLE_CLIENT_ID` (iOS bundle ID), `EVENSIES_APPLE_SERVICES_ID` (web Services ID)}; for `/auth/google`, `EVENSIES_GOOGLE_CLIENT_IDS` ∪ {`EVENSIES_GOOGLE_WEB_CLIENT_ID`} (empty values left out). If both are empty, 400 `AUTH_NOT_CONFIGURED` as now. Any other `aud` gets 401. Apple groups the Services ID under the primary App ID, so web and iOS get the same `sub` (the same user). On phones, `google_sign_in` already uses the web client id as `serverClientId` and gets tokens with that `aud`, so `EVENSIES_GOOGLE_WEB_CLIENT_ID` is usually a value already in `EVENSIES_GOOGLE_CLIENT_IDS` (it is a union, so overlap is fine). Google's `sub` is one per account, so web and phone get the same one.
- Token refresh (app, set in phase 9): concurrent 401s wait on one shared refresh `Future` (same as now). If the refresh fails with 401 but the saved refresh token changed in the meantime (another tab or another request refreshed first), the app does not clear the session. It resends that request once with the saved access token. If the saved token did not change, `clearSession()` as now. Two web tabs share one drift DB, so this rule keeps them from signing each other out.

Access 15 minutes, refresh 30 days. JWT HS256, the secret is `EVENSIES_JWT_SECRET`.

### Review sign-in
App store reviewers (Google Play in particular) don't create accounts or use their own Google or Apple account, and the official server has no email sign-in at launch. So the operator can give reviewers one username and password, entered in the store console (Play Console → App access, App Store Connect → App Review Information). Added after phase 11 ([Official server](#official-server-app-only)).
- Config: `EVENSIES_REVIEW_LOGIN_USERNAME` and `EVENSIES_REVIEW_LOGIN_PASSWORD` (`evensies.auth.review-username` / `review-password`, empty by default). **On only when the username is not blank and the password has at least 20 characters** (code points). The username is trimmed (a stray space in `.env` doesn't lock reviewers out). A username with a shorter password keeps it off, and the server logs one `WARN` at startup that says so (never the values). Turning it off again = clearing the variables and restarting; `POST /auth/refresh` then refuses the review account's sessions (401 "Account no longer exists"), so nobody keeps it. Changing the password or the username does **not** end its sessions (a new username is a new account, the old one stays signed in): before the change, sign in with Demo sign-in and use Settings → Sign out on all devices (`POST /me/logout-all`) or Delete account.
- `GET /info` → `"reviewLogin": true` exactly when it is on. The app shows a small "Demo sign-in" text button on the sign-in screen only then. Offline, the app uses the last saved `/info` answer for that server; a response without the key (older server), or no saved answer, means `false`. If the server answers 404 because it was turned off since, the dialog shows the generic error and the app reads `/info` again (the button goes).
- `POST /auth/review`, public (no token, like `/auth/apple`). The checks, in order:
  1. Off → 404 `NOT_FOUND` "No such endpoint", the same answer as an unknown path, whatever the body (POST only: other methods get 405, as on any existing path).
  2. `Content-Type` not `application/json` → 400 `VALIDATION`, not counted (a cross-site form post has no CORS preflight and must not use up the limits).
  3. Rate (abuse cap, in-memory `RateLimiter`s): per client IP (IPv6: per /64) 10 per minute and 20 per hour, then 100 per hour across all IPs. Every attempt counts, right or wrong, malformed included; an attempt refused by its IP's limit doesn't use the shared one. The hourly per-IP cap keeps one IP to a fifth of the shared budget, but a few IPs together can still use it up and lock reviewers out with 429 until it refills; the source is public and `/info` says it is on, so turn it off between reviews if that happens. Over → 429 `RATE_LIMITED`.
  4. The body (at most the first 4 KB is read) is not a JSON object, or `username` or `password` is missing, `null` or not a string → 400 `VALIDATION`.
  5. Wrong username or wrong password → 401 `UNAUTHORIZED` "Wrong username or password", the same body for both (the app shows "Wrong username or password"). Compared in constant time: the SHA-256 of each given value against the SHA-256 of the configured one with `MessageDigest.isEqual`, both before deciding. Case matters; spaces around the username are ignored (the server trims both sides, the app trims what is typed), the password must match exactly.
  6. → 200 `{"accessToken","refreshToken","user": UserDto}`, the same as `/auth/apple`.
- The account: one user with provider `review` and subject `review:<username>` (a new username is a new account). It is an ordinary account: the first sign-in has an empty `displayName` (the app asks for a name), `DELETE /me` works as for anyone, and signing in again after that reopens the same id, empty (no name, no groups). Reviewers share it, so it may hold what an earlier review left. For the same reason it can't hold an email address: `POST /me/email` → 403 `FORBIDDEN` (checked after `EMAIL_NOT_CONFIGURED`).
- No new error codes. The `dev` profile and `/auth/dev` are unchanged.

## Groups
| Method | Path | Request | Response |
|---|---|---|---|
| POST | `/groups` | `{"id","name","defaultCurrency","memberId","memberName"}`. id and memberId are generated by the app, `name` is 1–100 characters | `GroupDto` (`group.created` and `member.added` events are recorded at seq 1 and 2) |
| GET | `/groups` | | `[GroupSummaryDto]` |
| GET | `/groups/{id}` | | `GroupDto` |
| POST | `/groups/{id}/invite/rotate` | | `{"inviteCode"}` |
| GET | `/invites/{code}` | No auth needed | `{"groupId","name","kind","memberCount","members":[{"id","name","linked":bool}]}` |
| POST | `/invites/{code}/join` | `{"memberId": "<existing placeholder member>"}` or `{"newMemberId","name"}` | `GroupDto`. Records a `member.linked` or `member.added` (with userId) event. Phase 6: in a friend group, `newMemberId` gets 409 `LIMIT_EXCEEDED` (2 members). A placeholder claim is accepted without the group limit check and inserts a `friendships` row (see "Friends" below) |

```
GroupDto        {"id","name","defaultCurrency","inviteCode","createdAt","latestSeq","myMemberId","simplifyDebts","defaultSplit","kind","type","coverImageId","deleted"}
GroupSummaryDto {"id","name","defaultCurrency","latestSeq","memberCount","kind","type","coverImageId","deleted"}
```
- `kind` (phase 6): `"group"` (a regular group) or `"friend"` (a friend group, see "Friends" below). It is in `GroupDto`, `GroupSummaryDto`, the snapshot's `group` and `GET /invites/{code}`. The app reads a response without the key (older server) as `"group"`. It is set when the group is created and never changes (applier rule 13). `POST /groups` always makes `"group"`, and only `POST /friends` makes friend groups. The app's Groups tab shows only `"group"`. Friend groups show up as people in the Friends tab (opening `/groups/{id}` redirects to the friend page).
- `simplifyDebts` (boolean, default `true`) and `defaultSplit` (`SplitSpec|null`, default `null`, see "SplitSpec" below) are group settings. They are in the responses of `POST /groups`, `GET /groups/{id}` and `POST /invites/{code}/join`, and in the snapshot's `group` (not in `GroupSummaryDto`). The app reads a response without the two keys as the defaults. `POST /groups` creates the group with the defaults (the request has neither key).
- No endpoint changes group settings (name, default currency, simplify debts, default split). They change through the `group.updated` event, and any group member can send it (there are no admins). The default currency can no longer change once any expense or payment exists, deleted ones included (applier rule 12).
- **Leaving a group** = `member.removed` for your own member. The server handles it exactly like removing another member (only the app checks that the balance is 0; from phase 4, 0 in every currency, see "Balances per currency"). After that, the group drops out of `GET /groups` and its endpoints return 403. The member who left stays as removed (the user link stays too) and stays in balance calculations (rule 5). Rejoining by invite makes a new member (or claims another placeholder member). Phase 8: if I am in the template of an active recurring series (an amount above 0 in `payers` or `shares`), the app blocks leaving (after I leave, the series would keep creating my share, and nobody could settle that debt): `You're still in 2 repeating expenses (Rent, Netflix) · edit the latest one or stop them first` (names come from `seriesNames`, up to 3, then `and N more`). The settings screen checks before the tap, and `leaveGroup` checks again after syncing, next to the balance check. The server does not check.
Limits: 50 members per group, 100 groups per user → 409 `LIMIT_EXCEEDED` when exceeded. Phase 6: the 100 per user counts only `kind = 'group'` (`POST /friends` and friend-group claims skip this check). Instead, placeholder friends are limited to 200 per user (see "`POST /friends`" below). A friend group has exactly 2 members. Phase 8: 100 recurring series that are not stopped per group (`recurrence.created`, see "Recurring expenses" below).

Invite codes: **6 characters, alphabet `23456789ABCDEFGHJKMNPQRSTUVWXYZ`** (no 0/O, 1/I/L). 10-character codes issued earlier stay valid. `/invites/{code}`, `/invites/{code}/join` and `/j/{code}` normalize the code (uppercase it and remove everything except letters and digits: `k7p-4qx` = `K7P4QX`). The three endpoints are limited to **10 per minute per client IP** (`EVENSIES_INVITE_RATE_PER_MINUTE`). Over the limit: 429 `RATE_LIMITED`.

Friend codes (phase 6, `users.friend_code`) use the same alphabet, length and normalization. They share one namespace with group invite codes: a new code is used only if it is in neither `groups.invite_code` nor `users.friend_code` (`GroupService.newInviteCode` also checks both tables). So a code is a group or a friend, never both. **One** per-IP bucket is shared by the three invite endpoints and the friend code lookups (`GET /friend-invites/{code}`, `GET /f/{code}`, `POST /friends {code}`) (it moves from a field in `InviteController` to a bean). The app's code entry field calls `/invites/{code}` first and `/friend-invites/{code}` on 404, so one friend code uses 2 requests.

## Events (sync)
### push
`POST /groups/{id}/events`
```
Request: [{"clientId":"uuid","type":"expense.created","payload":{...},"createdAt":"2026-10-10T09:00:00Z"}]
Response: {"results":[{"clientId":"uuid","seq":12}], "latestSeq": 12}
```
- The whole array is one transaction. The server locks the group row with `SELECT ... FOR UPDATE`, then assigns seq.
- `(group_id, client_id)` is UNIQUE. A duplicate returns the existing seq (not an error).
- In the same transaction, the server applies the events to the tables (member/expense/expense_share/payment/comment, phase 7 attachment, phase 8 recurrence) and writes `meta` for the activity feed on the event row ("Activity and notifications").
- Validation failures reject the whole array with 400 (the phase 7 receipt count limit is 409): a memberId outside the group, a split sum mismatch, a negative amount, the id of a creating event (`*.created`, `member.added`, `comment.added`, including phase 8 `recurrence.created`) already existing in another group, and in phase 7 an `attachment.added` that was not uploaded to this group. Only the server creates `group.created` (400 `VALIDATION` if the app pushes it). Other events (`updated`, `deleted`, `restored`, `linked`, `removed`, `confirmed`, including phase 7 `attachment.deleted` and `payment.restored`, and phase 8 `recurrence.updated` and `recurrence.deleted`) that point to an id in another group point to a target that does not exist in this group. So they pass and applier rule 4 ignores them (the other group does not change, and its receipt files are not deleted either). Rate limit: 120 events per minute per user → 429.
- Validation and error codes for payers, splits and group settings: "Payer, split and group settings validation" below. For recurring series (phase 8): "Recurring expense validation".
- An offline device never gets a 400 because of state it could not know about (changes someone else made first). Such cases are handled by applier rules (e.g. rule 12) or by server normalization (e.g. fixing `paidBy` to the main payer).

#### Rejected events (app)
So that one rejected event does not block the outbox forever, the app does the following.
1. If a push fails with **400 or 409**, resend the same batch in order, **one event at a time**. Delete each accepted event from the outbox right away (safe because clientId makes it idempotent).
2. If a single event still gets 400 or 409, drop it: write the error `code` to the outbox row's `rejected` (it is not resent and not applied locally again), show the user `Couldn't save {what}: {reason}`, then delete the row (if the app closes before showing it, show it at the next launch). {what} is a phrase per event type: `the new expense “Hotel”`, `a change to “Hotel”`, `deleting “Hotel”`, `a payment`, `a group settings change` and so on (`an expense` if the description is unknown). Phase 7: `attachment.added` → `the receipt on “Hotel”`, `attachment.deleted` → `removing a receipt from “Hotel”`, `payment.restored` → `restoring a payment`. Phase 8: `recurrence.created` → `repeating “Rent”`, `recurrence.updated` → `a change to future “Rent”`, `recurrence.deleted` → `stopping “Rent” from repeating` (the description comes from the payload's `template` or `fields`, otherwise from the local series' template; if unknown, `a repeating expense`, `a change to a repeating expense` and `stopping a repeating expense` respectively). If the first expense of a rejected `recurrence.created` (the `expense.created` with that `recurrenceId`) was accepted (normalization saved it without the series mark), show `“Water” was saved but won't repeat: {reason}` instead of `Couldn't save …` (so the user does not add the same expense again). If that expense was rejected too, use the message above as is. For a dropped `attachment.added`, also delete the receipt's local row and cache file (the phase 8 cleanup deletes the uploaded file left on the server).
3. If a push gets **403** or a pull gets **403 or 404**, first call `GET /groups/{id}`. If that is the server's own 403 `FORBIDDEN` or 404 `NOT_FOUND` (a response with an error body), I am out of that group (left or removed), so delete the group's local data without rejection handling (same as syncAll). If it is 200, the push's 403 is an event permission problem, so treat it like the 400 in 1 and 2. A response without an error body (`NETWORK`: a proxy, a captive portal and so on) is not a rejection; resend as in 4.
4. If a 401, 429, 5xx or network error happens while sending one at a time, stop there. Leave the remaining events in the outbox and resend them later, as now. (Resending one at a time uses the rate limit once more: N for the failed batch + N again.)
5. If any event was dropped, rebuild the group: after `adoptFromSnapshot`, apply the remaining outbox events (not sent yet, not dropped) in order. This makes sure no optimistic local change from a dropped event is left.

| code | {reason} |
|---|---|
| `SUM_MISMATCH` | the split doesn't add up |
| `PAYERS_SUM_MISMATCH` | the payers don't add up |
| `NEGATIVE_AMOUNT` | an amount is below zero |
| `UNKNOWN_MEMBER` | it refers to someone who isn't in the group |
| `UNKNOWN_CURRENCY` | the currency isn't supported |
| `MEMBER_TAKEN` | that member is already taken |
| `LIMIT_EXCEEDED` | the group is full (for phase 7 `attachment.added`: an expense can have at most 10 receipts; for phase 8 `recurrence.created`: a group can have at most 100 repeating expenses) |
| `ATTACHMENT_NOT_UPLOADED` | the photo didn't upload (phase 7) |
| `FORBIDDEN` | you're not allowed to make that change |
| Others (`VALIDATION` and so on) | the server refused it |

Phase 9: `Couldn't save {what}: {reason}` and the {what} and {reason} texts above are the English source strings in the ARB, shown in the UI language. Fragments are not joined. Each {what} has one whole sentence (`rejectedNewExpense(description)` and so on), each code has its own {reason} ARB string, and an unknown code uses `errorGeneric(code)`. The server's `message` is not shown.

### pull
`GET /groups/{id}/events?after=<seq>&limit=500`
```
Response: {"events":[{"seq","clientId","type","payload","actorUserId","createdAt"}], "latestSeq": 57}
```
- Phase 8: recurring expenses (`expense.created`) made by the server scheduler have `"actorUserId": null`, and their `createdAt` is that occurrence's `dueAt` (see "Recurring expenses" below). The app already reads `actorUserId` as `string|null`.
### snapshot
`GET /groups/{id}/snapshot`
```
{"group": GroupDto,
 "members":  [{"id","name","userId","removed":bool}],
 "expenses": [{"id","description","amount","currency","fxRateToDefault","paidBy","payers":[{"memberId","amount"}],"refund":bool,"split","date","category","notes","deleted":bool,"moved":bool,"recurrenceId","occurrence","shares":[{"memberId","amount"}]}],
 "payments": [{"id","fromMember","toMember","amount","currency","date","deleted":bool,"status","replaced":bool}],
 "comments": [{"id","expenseId","paymentId","authorMemberId","text","createdAt","deleted":bool}],
 "attachments": [{"id","expenseId","deleted":bool}],
 "recurrences": [RecurrenceDto],
 "latestSeq": 57}
```
- `recurrences` (phase 8, "Recurring expenses"): every series of the group, stopped ones included with `deleted: true`. The order is creation order (`created_at, id`). Scheduler columns (`next_occurrence`, `next_due_at`) are not sent. `template` is the stored JSON (it is jsonb, so the key order can differ). The app reads a response without the key (older server) as `[]`.
- `recurrenceId` (`string|null`) and `occurrence` (`int|null`) (phase 8): for an expense in a recurring series, the series id and the occurrence number (0 for the first expense; 1, 2, … for occurrences the server posts). Otherwise both are `null`. The app reads a response without the keys as `null`.
- `attachments` (phase 7, "Receipts"): only receipts attached to an expense (`attachment.added` applied), deleted ones included with `deleted: true`. Receipts uploaded but not attached yet are not included. The order is upload order (`created_at, id`), so it can differ from the order of replaying the log (only the display order differs). The app reads a response without the key (older server) as `[]`.
- `replaced` (phase 7) is `true` for a payment replaced by an edit (`payment.deleted` with `replacedBy`) (applier rule 7, always together with `deleted: true`), otherwise `false`. The app reads a response without the key as `false`.
- `paidBy` is the main payer (applier rule 10), `payers` has 1 or more entries (in the order sent), `refund` is a boolean, and `split` is `SplitSpec|null`. Expenses from before this phase have `payers: [{paidBy, amount}]`, `refund: false` and `split: null`.
- `moved` (phase 6) is `true` for an expense deleted by moving it (applier rule 13, always together with `deleted: true`), otherwise `false`. The app reads a response without the key (older server) as `false`.
- `notes` is `string|null`. `comments` includes deleted comments with `deleted: true` (same as expenses and payments). Of `expenseId` and `paymentId` (phase 6, payment comments), exactly one is a string and the other is `null`. Comments from before this phase have `paymentId: null`. The snapshot's `group` (`GroupDto`) has `kind`. The event shape in pull responses does not change (the server-internal `meta` is not sent).
- A deleted comment's `text` is `""` (an empty string) (applier rule 8). In the push transaction that stores `comment.deleted`, the server also sets the `text` in the payload of that comment's stored `comment.added` event to `""`. This is the only value in the log that changes after it is stored; seq, clientId and the rest of the payload stay. So the text is left nowhere: not in the snapshot, the export or a pull. The app clears the comment row's text and that comment's activity cache rows, and deletes outbox rows the server accepted (push succeeded).

### Event types and payloads
| type | payload |
|---|---|
| `group.created` | `{"name","defaultCurrency","kind"?: "group"\|"friend","type"?: "trip"\|"home"\|"couple"\|"other"}` (made by the server in POST /groups and POST /friends). `kind` (phase 6) is set to `"friend"` only by POST /friends. If missing, `"group"` (applier rule 13). `type` (phase 10) is the `type` of POST /groups; if missing, `"other"` (rule 17) |
| `group.updated` | `{"name"?: string, "defaultCurrency"?: string, "simplifyDebts"?: bool, "defaultSplit"?: SplitSpec\|null}`. Missing keys stay as they are, and `"defaultSplit": null` clears it (rule 11). `defaultSplit` modes are only `percent` and `shares`. Example (`expense.created`, two people pay and it is split 2:1:1 by shares):
```json
{"expenseId": "…", "description": "Hotel", "amount": 10000, "currency": "EUR", "fxRateToDefault": null,
 "paidBy": "m-anna",
 "payers": [{"memberId": "m-anna", "amount": 6000}, {"memberId": "m-ben", "amount": 4000}],
 "refund": false,
 "split": {"mode": "shares", "input": {"m-anna": 2, "m-ben": 1, "m-cara": 1}},
 "date": "2026-10-11", "category": null, "notes": null,
 "shares": [{"memberId": "m-anna", "amount": 5000}, {"memberId": "m-ben", "amount": 2500}, {"memberId": "m-cara", "amount": 2500}]}
```
```
SplitSpec {"mode": "equal" | "percent" | "shares" | "adjustment" | "itemized", "input"?: {"<memberId>": number}, "bill"?: ItemizedBill}
ItemizedBill {"lines": [{"name": string, "amount": int, "memberIds": [memberId]}], "tax": int, "tip": int, "discount": int}
```
- The amounts are always defined by `shares` and `payers`. `split` is a hint so the editor can reopen the expense in the same mode with the same numbers. The server does not recompute `shares` from `split`. When opening, the app uses that mode only if `computeSplit(amount, split.mode, memberIds of shares, split.input)` equals the stored shares (entries of 0 are left out of the comparison); otherwise it opens the expense as exact. `itemized` opens as Items only if `itemizedTotal(bill) == amount` and `computeItemizedSplit(bill)` equals the stored shares (entries of 0 are left out of the comparison) (see "Itemized split" below).
- `itemized` (phase 7, "Itemized split"): `bill` is required and `input` must be absent (`null` counts as absent). A `bill` sent with any other mode is ignored like any other key and stored as is. Example: `{"mode": "itemized", "bill": {"lines": [{"name": "Burger", "amount": 1450, "memberIds": ["m-anna"]}, {"name": "Fries to share", "amount": 700, "memberIds": ["m-anna", "m-ben"]}], "tax": 284, "tip": 600, "discount": 0}}`. The server does not check that the bill matches the shares (phase 3 principle). The app always sends `tax`, `tip` and `discount` (0 included) and reads a missing one as 0. It cannot be used in `defaultSplit`.
- `equal`: no `input` (or null). The people sharing the cost are in `shares` (only the checked members). The other modes put every member on the screen into `shares`, 0 included.
- `percent`: `input` = percentages. `shares`: `input` = share counts (decimals allowed). `adjustment`: `input` = adjustment amounts in minor units (can be negative, must be integer values: `1000` and `1000.0` are the same, and `1000.5` is 400). These three modes require `input`. A member missing from `input` is 0.
- An exact split (amounts typed in directly) is `split: null`. There is no mode `exact` (400).
- Other keys in `split` and `defaultSplit` (including other keys in `bill` and in its `lines[]`) are ignored and stored as is. The app reads an unknown mode as "no split" without an error (apps up to phase 6 read `itemized` that way).
- `defaultSplit` (the group's default split) uses only `percent` and `shares`. A new expense starts from `defaultSplit` if there is one, otherwise from equal with everyone checked. A member missing from `input` (someone who joined later) is 0. If that split cannot be computed (a sum error and so on), the expense starts from equal.
- `refund: true` = money received back (e.g. the hotel gave Anna €60 back). `payers` = who received it, `shares` = who gets a part of it. The balance effect is the opposite of an expense.
- Balances (app, `shared/settlement-cases.json`): per expense `sign = refund ? −1 : +1`, per payer `balance[m] += sign × payers[m]`, per share `balance[m] −= sign × shares[m]`. A payment does `balance[from] += amount` and `balance[to] −= amount`. Positive = is owed money.

- Character counts (`description` 200, `notes` 500, `text` 1000, group `name` 100, member `name` 100) are UTF-16 lengths (Kotlin and Dart `String.length`). 400 `VALIDATION` if `notes` is not a string or null or is too long, if `text` or `createdAt` breaks its rules, or if a group `name` (`group.created` and `group.updated`, so POST /groups too) or a member `name` (`member.added`, so also the `memberName` of POST /groups and the `name` of an invite join) is over 100 characters. Member name events already stored with a long name are still read (the check runs only when sending).
- Amount limit: an expense's `amount`, `payers[].amount` and `shares[].amount`, and the `amount` of `payment.created`, are at most `10000000000000` (10^13 minor units). Over that: 400 `VALIDATION`. A group has at most 50 members, so the sum of payers or shares can never overflow a 64-bit integer and wrap around to equal `amount`. The 200-character limit applies only to a newly sent `description` (other fields of an expense whose long description is already stored can still be edited). The Splitwise import cuts descriptions to 200 characters.
- JSON types (the app applier reads values without type conversion, so the server blocks wrong types; a violation gets 400 `VALIDATION`): for keys present in `expense.created` and `expense.updated.fields`, `description`, `currency`, `paidBy`, `date`, `category` and `notes` are strings, `amount` is an integer, `fxRateToDefault` is a finite number (a value that reads as infinity, like `1e999`, is 400), `shares` and `payers` are `[{"memberId": string, "amount": integer}]`, `refund` is a boolean and `split` is an object. In `group.updated`, `simplifyDebts` is a boolean (null is 400 too) and `defaultSplit` is an object or null. `null` is allowed as rule 9 says (in `expense.created`, other validation rejects null for keys that need a value). `expense.created` must have `amount` and `shares`. The `amount` of `payment.created` is an integer too. `name` in `group.*` and `member.added` is a string that is not only whitespace. In `expense.created`, `payment.created` and `comment.added`, the `deleted` key is absent or `false` (you cannot delete something while creating it). Phase 8: `recurrenceId` is a lowercase UUID string and `occurrence` is an integer (both can be `null`, see "Recurring expense validation" below). In `recurrence.*`, `recurrenceId`, `frequency`, `startDate` and `timeZone` are strings, and `template` and `fields` are objects.
- `category` (`expense.created`, `expense.updated.fields`) is `string|null`. Its meaning is in "Categories" below (phase 5): a key from `shared/categories.json`, `null` = General, any other string = older free text. The server only checks that it is a string or null (no value check, no conversion).
- The 1–1000 character check on the `text` of `comment.added` applies only when sending. Stored events of deleted comments are pulled with `text: ""` (applier rule 8).
- Compatibility: release 1 apps skipped `comment.*` and `expense.restored` as unknown types, dropped `notes`, and still moved lastSeq forward. So when the app DB moves to schemaVersion 3, the lastSeq of every group goes back to 0, and a pull that starts from lastSeq 0 replays the whole log **from an empty state** (replaying on top of the stored state would not bring back the notes of `expense.created`). While old apps are still in use, restored expenses look deleted in those apps.

Errors here are 400 and reject the whole array. Type checks run on the original payload. Sum and member checks run on the expense or group after the event is applied (same as existing checks such as `description`). For `expense.updated` on a deleted or missing expense, only the type checks run (rules 3 and 4 ignore it anyway).

|---|---|
| `PAYERS_SUM_MISMATCH` | After applying, Σ `payers[].amount` ≠ `amount` (e.g. an edit that changes only `amount` on an expense with several payers, rule 10d) |
| `UNKNOWN_MEMBER` | A payer, a key of `split.input`, a value in `split.bill.lines[].memberIds` (phase 7) or a key of `defaultSplit.input` is not a group member (removed members are members) |
| `NEGATIVE_AMOUNT` | A payer amount < 0 |
| `SUM_MISMATCH` | `defaultSplit` is percent and the sum is not 100 (±0.001). The sum of an expense's `split` is not checked (the `shares` sum check stays) |

### Applier rules
These rules are the same in the app (Dart) and the server (Kotlin), and `shared/sync-cases.json` checks them.
1. `applyEvent(state, event)` is a pure function. Applying the same event twice = applying it once.
2. Edit vs edit: per field, the higher seq wins (this holds naturally when events are applied in order).
3. Delete vs edit: `updated` on an expense or payment with `deleted=true` is ignored (the delete wins). Only `expense.restored` brings a deleted expense back, and `updated` events ignored while it was deleted do not come back after the restore.
4. `updated`, `deleted`, `restored`, `linked`, `removed`, `confirmed` and `comment.deleted` (including phase 8 `recurrence.updated` and `recurrence.deleted`) on a missing target are ignored.
5. `member.removed` only marks `removed=true`. The member stays in balance calculations.
6. `payment.confirmed` changes `status` to `confirmed`. It is ignored for a missing or deleted payment. Balances count `sent` and `confirmed` payments the same way (the app shows `sent` as "waiting for confirmation").
7. `expense.restored` sets `deleted=false` again. For an expense that is not deleted, it changes nothing. When a delete and a restore cross, the later one in seq order wins. Exception (phase 6): a moved (`moved`) expense is not restored (rule 13). Phase 7: `payment.restored` does the same for payments (`deleted=false`, `status` unchanged, so a `sent` payment waits for confirmation again; ignored for a live or missing payment). Exception: a `payment.deleted` whose `replacedBy` is a string (a payment edit) does a normal delete and also marks `replaced=true` (no later event clears it; a later delete without `replacedBy` leaves it as is), and `payment.restored` on a `replaced` payment is ignored (so it is not counted twice with the new payment the edit made). Default `replaced = false`.
8. `comment.added` appends the comment only when the `commentId` is new (if it exists, deleted comments included, the event is ignored; idempotent). `comment.deleted` marks `deleted=true` and empties `text` to `""` (the comment stays in the list). The `comment.added` in the server log also arrives with `text: ""` (see snapshot above), so devices that saw the text and devices that did not end up in the same state. The applier does not check that the expense exists (server validation guarantees it). Phase 6: a comment stores `expenseId` and `paymentId` as received (`null` if missing; a payment comment has `expenseId: null`). The applier does not check that the payment exists either.
9. Missing fields: if `expense.created` has no `notes`, it is `null`. `expense.updated` changes only the keys in `fields` (except `payers`, `paidBy` and `split`, see rule 10). For `notes`, `category`, `fxRateToDefault` and `split`, a `null` clears the value. A `null` for any other key (`payers` and `refund` included) is ignored.
10. Payers, refunds and split input.
    - `payers` is the source of truth, and `paidBy` is derived from it. **Main payer** = the payer with the largest amount; on a tie, the payer with the smallest memberId (ascending string order). The applier never trusts the payload's `paidBy` and always derives it again. `payers` keeps the order it was sent in.
    - `expense.created`: if `payers` is missing or null, `[{paidBy, amount}]`. If `refund` is missing or null, `false`. If `split` is missing, `null`.
    - Payers in `expense.updated` (expense not deleted, rule 3): (a) if `fields.payers` is present (not null), replace them with it. (b) Otherwise, if `fields.paidBy` is present, `[{paidBy, amount after this edit}]`. (c) Otherwise, if `fields.amount` is present and there is one payer, change that payer's amount to the new amount. (d) Otherwise, no change.
    - `refund`: changes if `fields.refund` is a boolean.
    - `split`: if `fields` has a `split` key, its value (null clears it). If not, and `fields` has `shares` or `amount` (with a non-null value), `null` (decided by the key alone, even if the value is the same). Otherwise, no change.
11. Group settings: in `group.updated`, missing keys stay, `simplifyDebts` takes its value, and `"defaultSplit": null` clears it. Defaults: `simplifyDebts = true`, `defaultSplit = null`. `group.created` does not change these two.
12. Currency lock: if the state has any expense or payment (deleted ones included, since they can be restored), the `defaultCurrency` of `group.updated` is ignored. Other keys in the same event are applied. The server accepts and stores this event without 400. Reason: every `fxRateToDefault` and payment amount is in the group currency. This rule looks at the state, so "applying the whole log once more on top of the final state" could give a different result (after `group.created` resets the currency, the change is ignored). Sync never does that (each event once in seq order, or from an empty state).
13. Group kind (phase 6): `group.created` sets `kind` (`"group"` if missing or not a string). No later event changes it (the server blocks a `kind` key in `group.updated` with 400, and the applier ignores it too). Default `kind = "group"`. Moves: an `expense.deleted` whose `movedTo` is an object sets `deleted=true` like a normal delete and also marks `moved=true` (no later event clears it; a later delete without `movedTo` leaves it as is). `expense.restored` on a `moved` expense is ignored (an exception to rule 7: the expense now counts in another group, so restoring it would count it twice). The server accepts and stores that `expense.restored` without 400 (it may be a restore made offline before the move). The state does not change, so the server hides it from the activity (hidden case 1). The app does not show Restore on a moved expense. Default `moved = false`.
14. Receipts (phase 7): the state has `attachments` (`{id, expenseId, deleted}`, in the order they were attached). Default `[]`.
    - `attachment.added`: if the `attachmentId` already exists (deleted ones included), nothing changes (idempotent; if it comes again after a delete, it stays deleted). If `expenseId` is an expense not in the state, it is ignored. Otherwise, append `{id, expenseId, deleted: false}` (receipts attach to deleted expenses too, so restoring the expense brings its receipts back).
    - `attachment.deleted`: ignored for a missing `attachmentId`; otherwise `deleted=true` (it stays in the list). The payload's `expenseId` is not read.
    - An expense's `deleted` and `moved` do not change its receipts (`expense.deleted` does not delete receipts).
15. Recurring series (phase 8): the state has `recurrences` (`{id, frequency, startDate, timeZone, template, deleted}`, in creation order). Default `[]`.
    - `recurrence.created`: if the id already exists (stopped ones included), nothing changes (idempotent; the first schedule and template stay). Otherwise, append `{id, frequency, startDate, timeZone, template: as received, deleted: false}` (other payload keys, for example `deleted`, are not read; phase 10 `remindDaysBefore` is covered by rule 18).
    - `recurrence.updated`: ignored for a missing or `deleted` series. Otherwise, for each key in `fields`, set that template key to the received value. `null` is stored as `null`; the key is not removed. Keys not in `fields` stay. Array and object values are replaced whole (Kotlin `template.deepCopy().setAll(fields)`, Dart `{...template, ...fields}`). There is no derived value like in rule 10.
    - `recurrence.deleted`: if the series exists, `deleted = true` (it stays in the list); if missing, ignored. No event undoes it.
    - Series events do not change expenses: editing the template or stopping the series leaves already posted occurrences as they are.
16. Series mark on expenses (phase 8): an expense has `recurrenceId` (`string|null`) and `occurrence` (`int|null`). Both default to `null` (older events).
    - `expense.created`: the received values (`null` if missing).
    - `expense.updated` (expense not deleted, rule 3): if `fields` has the key, set it to that value; `null` clears it (same as `notes` in rule 9). If the key is missing, no change.
    - The applier does not check whether the series exists or is stopped (server normalization removes missing series). `expense.deleted`, `expense.restored` and moves do not change the mark.
17. Group types, covers and deletion (phase 10): a group has `type` (default `"other"`), `coverImageId` (default `null`) and `deleted` (default `false`).
    - `group.created` sets `type` (`"other"` if missing or not a string). A string `type` in `group.updated` changes it.
    - `coverImageId`: if `group.updated` has the key, set it to that value (`null` clears it); otherwise no change.
    - `group.deleted` sets `deleted = true` and `group.restored` sets `deleted = false`. The later one in seq order wins. Neither changes members, expenses, payments or series, and other events on a deleted group are applied as usual (deleting only hides the group; it does not lock it).
    - The app shows an unknown `type` as Other.
18. Recurring expense reminders (phase 10): a series has `remindDaysBefore` (`int|null`, default `null`). `recurrence.created` sets it (`null` if missing), and `recurrence.updated` changes it if the key is present (`null` clears it). `recurrence.updated` on a missing or stopped series is ignored as now (rule 15). It is applied separately from `fields`.

Phases 4 and 5 add no applier rules. Phase 6 adds rule 13 (with the moved-expense exception in rule 7) and extends rule 8 to payment comments. Phase 7 adds rule 14 and extends rule 7 to payments (`payment.restored`, with an exception for payments replaced by an edit). Phase 8 adds rules 15 and 16 and extends rule 4 to `recurrence.*`. Phase 9 adds no rules. Phase 10 adds rules 17 and 18.
- Phase 4: `fxRateToDefault` is stored exactly as the received number (`0` is stored as `0`; `null` clears it per rule 9). Its meaning and how balances use it: see "Currency conversion" below.
- Phase 5: `category` is stored exactly as the received string (it is not converted to a key; `null` clears it per rule 9; see the category cases in `shared/sync-cases.json`). Its meaning: see "Categories" below.

## Currency conversion
Phase 4. Each expense has its own currency. If it differs from the group currency (D), the expense also has `fxRateToDefault`, the rate that converts it to D. There are no new event types.

### `fxRateToDefault`
- Meaning: **major units of D per 1 major unit of the expense currency** (a JPY expense in a EUR group: 1 JPY = 0.00563349 EUR → `0.00563349`). It is not a ratio between minor units. It has meant this from the start (older apps left out the decimal-digit difference in balances), and stored values are not fixed.
- `null` or `0` = not converted ("Not converted"). If the expense currency is the same as D, the value is ignored, whatever it is.
- Server validation: a finite number or `null` (infinity is 400 too). A negative number gets 400 `VALIDATION`. `0` is accepted (older clients may have sent it). The app does not accept 0 as input (the form rejects it).
- Automatic rate = `crossRate(perEur, from, to)` = `perEur[to] / perEur[from]` (the `rates` of `GET /fx` below), rounded to 6 significant digits (`double.parse(x.toStringAsPrecision(6))`, 1/177.51 → `0.00563349`). If either value is missing or 0 or below, there is no automatic rate. A rate typed in by hand is stored as is.
- If either `currency` or `fxRateToDefault` changes, the app puts **both** in `expense.updated.fields` (`"fxRateToDefault": null` when changing to D). Sending only `currency` would leave the old currency's rate in place because of rule 9.
- **Convert (convert one currency)**: for each non-deleted expense in that currency (≠ D) whose rate is `null` or `0`, the app puts `expense.updated {"expenseId", "fields": {"currency": that currency, "fxRateToDefault": r}}` (r > 0, both keys as the rule above says) into the outbox in one local transaction. The snackbar's Undo sends back the previous value (`null` or `0`) for each expense, in the same shape. This usually goes out in one push (the outbox sends 100 at a time), so receivers get one notification (2 or more become the grouped sentence `{A} made {n} changes`), and the activity feed shows an `exchange rate` change for each expense. The limit of 120 events per minute per user still applies (anything over it stays in the outbox and goes later).
- Converted amounts are not stored anywhere. They are always computed again from the amount in the expense currency and the rate.

### Conversion rules
Test cases: `shared/fx-cases.json`. The functions are `convertAmount` and `convertExpense` in Dart `app/lib/domain/fx.dart` (written by the maintainer) and Kotlin `money/Fx.kt` (ported by Claude; the server uses it from phase 6 reminders and phase 10 summaries on). All are implemented, and `shared/` has no `"pending"` cases (phase 7 removes the fallback code from the stub days: `tryCore`, `implemented`, `fxReady`, `notImplementedLabel`, the Kotlin `NotImplementedError` catch, and the skipping of `pending` in tests). They are pure functions and take the decimal digits as arguments (`shared/currencies.json`).
- `convertAmount(amount, fromDecimals, toDecimals, rate) → int`: exact value = `amount × R × 10^(toDecimals − fromDecimals)`. R is the decimal number that `rate.toString()` prints (Dart prints the shortest round-trip form, so exponent forms like `7e-7` appear too; Kotlin uses `BigDecimal(rate.toString())`, and `Double.toString` in JDK 19+ is also shortest round-trip, so it is the same number). Do not use double multiplication (100 × 0.285 = 28.499999999999996, but the answer is 29). Round to the nearest integer; exactly .5 rounds away from 0 (28.5 → 29, −28.5 → −29). If rate is not finite or is 0 or below, `FxException('BAD_RATE')`. amount can be negative (balances).
- `convertExpense(amount, parts, fromDecimals, toDecimals, rate) → {amount, parts}`: check order `BAD_RATE` → `NEGATIVE_AMOUNT` if amount or a part is negative → `SUM_MISMATCH` if Σ parts ≠ amount. total = `convertAmount(amount)`. Round each part's exact value down. The remaining `total − Σ floors` units (from 0 up to the number of parts) go 1 each to the parts with the largest dropped fractions first (ties by ascending memberId; parts that are 0 get none). The result has the same keys as `parts`, and its sum is total.

### Balances per currency
The app (`domain/balances.dart`) and, from phase 6, the server (`Balances.ofGroup`) use the same rules.
D = the group's default currency. Only non-deleted expenses count.
1. A D expense goes into the D bucket as is (any rate left on it is ignored).
2. A foreign-currency expense with `fxRateToDefault > 0` is converted to D with `convertExpense` and goes into the D bucket. It is called once for the shares (`shares`) and once for the payers (`payers`), with the same amount, rate and digits (both totals are the same). If either call throws `FxException`, go to 3.
3. Any other expense goes into the bucket of its own currency, and `unconverted[currency]` goes up by 1.
4. A payment goes into the bucket of `payment.currency`. In phases 4 and 5, Settle up always made payments in D. From phase 6, it makes them in each bucket's own currency (below).
5. The D bucket always exists. Other buckets stay only while someone's balance in them is not 0. In each bucket, the balances add up to 0.
- Each bucket runs `computeBalances` on its own (multiple payers and refunds included), then debt simplification (`simplifyDebts`), or pairwise for groups that turned it off. No expense is left out (phase 7: removes `unsupported` and its notice line).
- Settle up (phases 4 and 5) showed payments only for the D bucket, and the other buckets were one card ("¥3,000 isn't converted yet · Convert"). **Phase 6**: it shows payments for every bucket and records them in that bucket's currency (D bucket first, then the other buckets under "Not converted · JPY" in currency code order). So debts that are not in the group currency can be settled in their own currency without converting (parity #76). If that bucket has expenses without a rate, Convert shows too. Payment links open in that bucket's currency (phase 1 link rules unchanged: EPC QR only for EUR, IBAN in other currencies is copy only).
- Convert does not change payments: if you settle in X and then convert the X expenses, only the X payment stays in the X bucket, and it looks like a debt in the opposite direction. So the Convert sheet shows the line `Payments in JPY stay in JPY` when that currency has non-deleted payments.
- Server (phase 6) `money/Balances.kt`: `ofGroup(state)` = a port of `balancesOf`, `transfers(result, simplify)` = `groupTransfers` (for groups that turned it off, a port of `pairwiseDebts`; Kotlin also checks `expectedPairwise` in `shared/settlement-cases.json`). If conversion throws `FxException`, that expense stays in its own currency's bucket, like Dart `tryFx`. `Settlement.balances` counts multiple payers and refunds, so there is no `unsupported`.
- Leaving a group: my balance must be 0 in every bucket (unconverted expenses by themselves do not block it). From phase 6, other buckets can also be settled in their own currency, so leaving needs no conversion (app notice `You owe ¥3,000 · settle up in JPY first`).
- The "≈" in home currency H: the sum over each of my buckets X of `convertAmount(balance, digits(X), digits(H), crossRate(latest table, X, H))`. Hidden if any rate is missing or only H is involved.

## Exchange rates
Phase 4.

| Method | Path | Request | Response |
|---|---|---|---|
| GET | `/fx?date=YYYY-MM-DD` | `date` is optional. Missing or in the future means today (UTC) | `FxTable` |

```
FxTable {"date": "2026-10-10", "base": "EUR", "rates": {"EUR": 1.0, "USD": 1.1217, "JPY": 177.51, ...}}
```
- `rates`: major units of that currency per 1 major unit of EUR. Only codes in `shared/currencies.json` appear, and codes the source does not publish may be missing. `EUR` is always `1`. Values are exactly what the source gave (no rounding).
- `date`: the latest rate date in the table (on or before the requested date). The source (Frankfurter v2) can have a different last publication date per currency (weekends, holidays, publication by each source). The app shows this value as "rate of {date}" and uses it as the local cache key.
- `base` is always `"EUR"`.
- Auth required (401). Any signed-in user, regardless of group.
- Errors: a date not in `YYYY-MM-DD` format or not a real date → 400 `VALIDATION`. A per-user bucket of 30 that refills 0.5 per second (30 per minute); requests answered from the cache count too → 429 `RATE_LIMITED`. No rates → 503 `FX_UNAVAILABLE` (below).
- The app never calls Frankfurter directly. Only the server does.

Server cache `fx_days` (one row for the requested day D, D = `date` capped at today (UTC)):
1. If `EVENSIES_FX_URL` is empty, 503 `FX_UNAVAILABLE` without looking at the DB or the source (automatic rates off).
2. If the D row exists and is **final** (`fetched_at ≥ D + 2 days 00:00 UTC`, that is, fetched after the day after D ended) or **recent** (`fetched_at > now − 6 hours`), return it as is. (This is how the design's "if before yesterday, keep it as is" was pinned down. It keeps a row fetched early on day D from being stuck with the previous day's rates.)
3. Otherwise `GET {EVENSIES_FX_URL}/rates?base=EUR&date={D}` (a trailing `/` is ignored; connect and read timeouts are 5 seconds each). Success = 200, the body is a JSON array `[{"date","base","quote","rate"}]`, and at least one entry has a `quote` in our list (EUR excluded) and a positive `rate`. Keep only those entries and add `EUR: 1` to make `rates`. Upsert the D row with those `rates`, the largest `date` of the kept entries as `rate_date`, and `fetched_at = now`, then return it.
4. On failure (connection failure or timeout, not 200, parse failure, no entries left; the source returns `[]` for days without data, such as before 1999), return the D row if there is one, even an old one; otherwise 503 `FX_UNAVAILABLE`. A row from another day is never used instead (the app picks from its own cache). For a failed D, the server does not ask the source again for 5 minutes and gives the same answer right away (the old row or 503) (kept in server memory, forgotten on restart). This keeps every request from being held for up to 10 seconds while the source is down.
- So the source is called once for a past day (once the row is final, that is it), and at most once every 6 hours for today and yesterday. There is no scheduler. Two requests for the same D at the same time may both call the source; the upsert makes that safe.
- On the server, `FxService` is the only place that reads `fx_days` (the phase 8 recurring expense scheduler reuses it).

App (local cache drift `FxDays`, key = the response's `date`):
- Online: ask the server (3-second timeout) and store the received table. If the app is online when it starts, it fetches the latest table (without `date`) once.
- Offline or error (503 and 429 included): the latest row whose key is on or before that day; if none, the latest row; if none, no automatic rate ("offline · rate of {date}" or "No automatic rate. Enter one, or leave it empty to keep this under Not converted.").

## Categories
Phase 5. No new event types, fields, endpoints, migrations or error codes. This section only defines what the values of an expense's `category` (`string|null`) mean.

### Taxonomy (`shared/categories.json`)
- Splitwise's taxonomy as is: 7 parents (`parents[]`) and 43 subcategories (`categories[]`). There are no user-defined categories.
- The copies `app/assets/categories.json` (the app reads it at startup, next to `Money.loadFromAssets()`) and `server/src/main/resources/categories.json` must be byte-identical (tested on both sides, the same way as `currencies.json`).
- `key`: the value stored in `expense.category`. Only keys in `categories[]` are expense categories (the parent key `food` is not). Keys are never renamed or removed.
- `label`: English. Phase 9: the name on screen and in activity sentences is `categories[key]` in `shared/strings.json` (7 parents + 43 subcategories, per language; the `en` value must equal this `label`, tested on both sides). It is not in the ARB (because the server push `category X → Y` uses the same names). When `*.other` is shown outside its parent heading (`labelOf`, change notation, insights), it is `words.categoryOther` (`{parent} - Other`, `{parent}` = the parent name in that language). The label comparisons in `resolveCategory`, `keyForLabel` and `guessCategory`, the CSV export and the Splitwise import still use this English `label` (stored legacy text was written in English, and exported CSVs must be importable again). Search (phase 5) matches the name in the UI language and its parent's name (`shared/search-cases.json` is `en`). `icon`: a Flutter Material icon name (`Icons.<icon>`). Categories without one (`*.other`, `uncategorized.general`) use the parent's. `keywords`: for guessing; written the way people write them, and folded when read.
- File order = picker order = tie-break order for guessing.

### What the values mean
| Stored value | Meaning | On screen |
|---|---|---|
| A key in `categories[]` | The value the new app writes | That category |
| `null` | General | General |
| Any other string (older free text, parent keys included) | legacy | Shown as General (text equal to a label shows as that category, see `resolveCategory` below); kept as the original text in storage, exports and snapshots |

- **The server does not check it** (on purpose). A 400 would reject the whole batch from apps already installed. As now, it only checks for a string or null. The applier also stores the received value as is (see "Applier rules" above).
- Values the app sends: the chosen key (`"uncategorized.general"` when General is chosen), a guessed key, or `null` if nothing was chosen or guessed. A legacy value stays as is unless the user changes it in the picker; until then `category` is not put in `expense.updated.fields` (only changed fields are sent).
- Guessing in the form: for a new expense, or an expense whose stored value is `null`, as long as the user has not chosen yet, the app fills the chip with `guessCategory` 300ms after the description changes (history = the group's non-deleted expenses in state order, without the expense being edited) and marks it "auto". Clearing the description clears the guess too. Once the user chooses (General included), there is no more guessing. Expenses with a stored key or legacy value are not guessed.

### Category rules
App: `domain/categories.dart`. Server: `export/Categories.kt`. Cases: `shared/category-cases.json`.
- `fold(s)`: lowercase (Dart `toLowerCase`) → remove combining marks U+0300–U+036F → a letter in U+00C0–U+017F becomes the first character of its Unicode canonical decomposition (`é→e`, `ñ→n`, `ź→z`); letters without a decomposition map as `ß→ss, æ→ae, œ→oe, ø→o, ł→l, đ→d, ð→d, þ→th, ı→i, ħ→h, ŧ→t, ĸ→k, ŀ→l, ŉ→n, ŋ→n, ĳ→ij, ſ→s`. Other characters (`×`, Chinese characters, Hangul and so on) and whitespace stay as they are.
- `resolveCategory(raw) → key` (app): `t = raw.trim()`. If `t` is a key in `categories[]` (case-sensitive), the result is `t`. Otherwise, if `t` lowercased equals a label (lowercased) that **appears only once** among the labels in `categories[]`, the result is that key. Here the labels of the six `*.other` entries count as `{parent label} - Other` (`Entertainment - Other`, the same form as the server CSV), so a bare `Other` matches none of them. Parent labels are not checked. Everything else (`null`, `""`, parent keys and labels included) is `uncategorized.general`.
- Server `Categories.label(key)`: the label of a key in `categories[]`, where only the six `*.other` entries get `{parent label} - Other` (`Entertainment - Other`, so they stay distinct in the CSV); otherwise `null`. `Categories.keyForLabel(raw)`: the same as `resolveCategory`, except that the last step gives `null` (the import keeps the original text). So both sides read `{parent label} - Other` (case-insensitive) as that `*.other` key (`keyForLabel(label(k)) == k`; in the app, `resolveCategory(labelOf(k)) == k`). A bare `Other` is still `null`. Labels are English, so Kotlin `lowercase()` and Dart `toLowerCase()` give the same result.
- `guessCategory(description, history) → key|null` (app):
  1. `n(s)` = `fold(s)`, trimmed, with each run of whitespace collapsed to one space. If `n(description)` is empty, `null`.
  2. **History first**: in history (oldest first), the category of the **last** entry with the same `n(description)` whose category is a key in `categories[]`.
  3. **Tokens**: the non-empty pieces of `fold(text)` split by `[^\p{L}\p{N}]+` (unicode). Keywords are folded and split the same way.
  4. **Scripts written without spaces**: if a folded keyword has Chinese characters, Hiragana, Katakana, Hangul or Thai script, it matches when it is a substring anywhere in the whole folded description (this counts as an exact match). Score = the keyword's rune count.
  5. **Other keywords**: a keyword matches when its tokens appear in a row in the description's tokens. Every token but the last must be equal. The last token must be equal (exact), or the keyword token has 4 or more characters and the description token starts with it and is at most 2 characters longer (prefix). Score = the sum of the rune counts of the keyword tokens (the letter count without spaces).
  6. **Pick**: the highest score. On a tie, exact > prefix, then file order (the earlier category), then keyword order. If nothing matches, `null`. ("car rental" 9 beats "rent" 4.)

## Search (app only)
Phase 5. There is no server search endpoint. The app searches its local DB (the state of all groups), so search works offline too. `searchDocs`, `shared/search-cases.json`.
- Documents: one `SearchDoc {id, groupId, date, description, notes, comments, category, amount, currency}` per non-deleted expense. `comments` is the text of the non-deleted comments, `category` is the stored original text, and `amount` is in the expense currency as is (not converted; refunds are positive too). Payments and member names are not searched.
- **Every** term of the query (split by whitespace) must match. A term matches if its folded value is a substring of one of these, folded: description, notes, each comment, the original category, the resolved label or its parent label.
- Amounts: if a term matches `^\d+([.,]\d{1,3})?$`, it can also match as an amount. For the number N with k decimal places (`,` is a decimal point) and the currency's digits d (`decimals` in `shared/currencies.json`): `k ≤ d` and `amount ~/ 10^(d−k) == N·10^k`. `12` = €12.00–€12.99, `12,5` = €12.50–€12.59, `12,50` = €12.50, JPY `12000` = ¥12,000. A term too long to read as an integer does not match as an amount.
- Filters: `category` is a subcategory key (same resolve result) or a parent key (the resolve result starts with `{parent}.`; `uncategorized` also catches `null` and legacy values). `month` is `YYYY-MM` (the first 7 characters of `date`).
- If the query is empty and there are no filters, `[]` (every document for phase 10 `all`). Results are sorted by date descending, then by id ascending. `ponytail:` linear scan, 150ms debounce. Past about 20,000 expenses, use SQLite FTS5.
- Screen: `/search?group=&category=&month=&all=` (all optional). Opened from the group list, it searches all groups. Opened from a group screen, it searches that group (a removable chip). `all=1` (phase 10, **All expenses** in the wide web layout): shows the expenses of all groups in the order above even with nothing typed, and typing narrows them as usual ("No expenses yet" if there are no expenses).

## Insights (app only)
Phase 5. Totals and bars per group. No server changes. `computeTotals`, `shared/totals-cases.json`.
- **Buckets per currency** (the same buckets as "Balances per currency"): D bucket = `convertToDefault(state).converted` + D payments. Bucket for another currency X = unconverted X expenses (`unconverted[X]`) + X payments. `computeTotals` is called separately for each bucket. The screen shows the D bucket on top and the other buckets under "Not converted · JPY", with totals in their own currency. No amount is dropped.
- `computeTotals(expenses, payments, me) → {months: {YYYY-MM: PeriodTotals}, allTime}`. `computeTotals` does not look at currencies (it gets only one bucket).
  - Deleted expenses and payments are left out. Month = the first 7 characters of `date`.
  - Per expense, `sign = refund ? −1 : +1`. Add `sign × amount` to `spent` and to `byCategory[resolveCategory(category)]`, `sign × (my amount in payers)` to `youPaid`, `sign × (my amount in shares)` to `yourShare`, `sign × (m's amount in payers)` to `byMember[m].paid`, and `sign × (m's amount in shares)` to `byMember[m].share`.
  - Paid amounts are always read from the stored `payers` (`paidAmounts(Expense)`). They do not go through `computeBalances`, so expenses with several payers and refunds count in the totals too.
  - A payment (`sent` and `confirmed` alike) adds only to `paymentsMade` if I am `fromMember`, or only to `paymentsReceived` if I am `toMember`.
  - `netChange = youPaid − yourShare + paymentsMade − paymentsReceived`. `allTime` = the sum of all months. `byCategory` and `byMember` drop entries that are 0 after summing (for `byMember`, members whose paid and share are both 0). Month values can be negative because of refunds (bars start at 0; the amount text shows the value as is).
  - `allTime.netChange` equals my balance in that bucket (tested).
- **Who pays next**: `whoPaysNext(D bucket balances, ids of members not removed) → memberId|null` = the member with the most negative balance; on a tie, the smallest memberId; `null` if no balance is negative. One line at the top of the Balances tab: `{name} should pay next (owes {M(−balance)}, the most)`, or `You should pay next (you owe {M(−balance)}, the most)` if that member is `me` (no pronouns, because the gender is unknown; app only, translated in phase 9). Hidden if `balancesOf` is null.
- **Share a summary**: text with the period totals, top categories and balances, sent to the share sheet (`share_plus`). App only.

## Recording and editing payments
Phase 6. No new event types. It uses `payment.created`, `payment.deleted` and `comment.added`.
- **Record any payment** (**Record a payment** in Settle up, app `features/settle/payment_sheet.dart`): From and To (any two different members who are not removed), Amount (> 0), Currency (any currency in `shared/currencies.json`, default D; opened from a payment card in Settle up, the sheet is filled with that card's from, to, amount and currency), Date (default today, can be changed). One `payment.created`.
- **status** (set by the app): `"sent"` if From is my member and To is a member linked to another user (the receiver confirms, as in phase 1). Otherwise `"confirmed"` (I am the receiver, it was sent to a placeholder, or it records a payment between two other people). The server normalization (`confirmed` if the receiver is a placeholder or is the sender) stays as it is.
- **Edit** = `payment.deleted {"paymentId": old id, "replacedBy": new id}` for the old payment (`replacedBy` from phase 7) + `payment.created` with the new id, put into the outbox in one local transaction (there is no `payment.updated`). The old payment becomes `replaced` and cannot be restored (applier rule 7). Tapping a payment opens the same sheet for editing. Edit and delete show only for users linked to the payment's From or To (in the app; the server's `payment.deleted` permission is unchanged from phase 1). The new payment's status is set again by the rule above (if the sender edits it, it waits for confirmation again). It usually goes out in one push, so the receiver gets one notification, `{A} made 2 changes`. Activity (phase 7): the delete of the old payment is `payment_edited` (`{A} edited a payment of …`, so it does not read like a delete), and the new payment is `payment_added`. The detail title of the old payment is `Edited payment` (banner `This payment was edited`). Apps up to phase 6 do not know the kind and show `{A} made a change`.
- After an edit, the old payment's comments stay on the old (deleted) payment (they are not moved). When the user edits a payment that has comments, the sheet shows the line `Comments stay with the old payment`.
- **Restore a deleted payment** (phase 7, parity #110) = `payment.restored {"paymentId"}`. It sits in the same places as expense restore (phase 2): a SnackBar **Undo** for 10 seconds after a payment is deleted (not for the delete inside an edit; an edit is fixed by editing again), the banner `This payment was deleted` + **Restore** on a deleted payment's detail screen, and **Restore** on the payment's most recent `payment_deleted` row in the activity list. All three show only when the payment is currently deleted and not `replaced`, and the viewer is a user linked to its From or To (the server permission is the same as `payment.deleted`; the app does not know who created the payment, so it checks only From and To). The detail of a `replaced` payment shows only the `This payment was edited` banner, with no Restore. A restored payment keeps the status it had when it was deleted (if `sent`, the receiver confirms again). The activity is `payment_restored`. Local writes are the same as for expense restore (optimistic `deleted=false`, put into the outbox).
- **Payment detail** `/groups/:id/payments/:pid` (app): From → To, amount, date, status with phase 1 Confirm received / Not received, Edit and Delete (permissions above), and a comment thread (`comment.added {paymentId}`; same rules as expense comments: comments can be added to deleted payments too, and only the author can delete them). Tapping a `payment_*` item in the activity, a payment comment item or a recorded payment in Settle up opens this screen.
- **Settle up with a friend in one go** (**Settle up** on the friend page): from the ledger in "Overview" below (`GroupLedger.transfers`), collect the payments between me and that person, by group and currency (between one of my members and one of that person's members). Per currency, net = Σ(what that person owes me). One line per currency. A currency that has only unconverted buckets is also settled in that currency (with Convert too if there are expenses without a rate).
  - Recording = one `payment.created` per payment (that group, that currency, and that payment's from, to and amount). If it is a payment I make and the net for that currency is < 0, `"sent"` (phase 1 **I've sent it**). Otherwise `"confirmed"` (I am the receiver, **Mark as received**; and offsetting payments in the opposite direction of net, where no money actually moves).
  - The app puts them into the outbox and pushes them per group (each group has its own log).
  - If net < 0, payment method chips (phase 1): read with that person's member id from `GET /groups/{id}/payment-methods` of the friend group, or of one shared group if there is no friend group. `_pay` and `_bankSheet` move to `features/settle/pay_sheet.dart`.

```
FriendCode {"friendCode": "K7P4QX", "link": "https://evensies.nariinfo.dev/f/K7P4QX"}
```

- `link` = `EVENSIES_PUBLIC_URL` (without a trailing `/`) + `/f/` + the code. The app's link parser (`extractInviteCode`) reads `/f/<code>` and `evensies://f/<code>` as friend codes. Universal Links (`"/f/*"` in `apple-app-site-association`) and App Links (`host="f"`, `pathPrefix="/f/"`).
- Friend code: 6 characters ("Invite codes" above), one per user (`users.friend_code`, UNIQUE). Set to `NULL` when the account is deleted.
- **Shared group** = a group where both users have a member row linked by `user_id` (removed rows included, any `kind`). Profile photo and reminder permissions use this definition. Adding a friend by `userId` is narrower: it counts only shared groups where neither row is removed (a friend group cannot be left and shows each other's payment methods, so people who left or were removed are not added without their consent).

**`POST /friends`**
- `id`: a new group UUID made by the app (idempotent on retry, same as `POST /groups`). If a group with that id already exists, the server returns that group without other checks (403 if the caller is not a member).
- `defaultCurrency`: the default currency for a new group (the app sends the home currency). Required; if it is not in the list, 400 `UNKNOWN_CURRENCY`. Not used when an existing friend group is returned.
- One of the three (`null` counts as absent; if all three are absent, two or more are present, or the value is not a string, 400 `VALIDATION`):
  - `code`: a friend code (normalized). Unknown code: 404 `NOT_FOUND`. Uses the per-IP bucket above (429).
  - `userId`: a user who is in a shared group with the caller right now (neither member removed). An unknown id, a deleted account and no such shared group all get 403 `FORBIDDEN` (the server does not reveal whether the user exists).
  - `name`: a person who does not use Evensies yet (a placeholder friend). 1–30 code points after trim, otherwise 400 `VALIDATION`.
- If the code or userId belongs to the caller, 400 `SELF_FRIEND`.
- Rate: each call uses 3 from the per-user event bucket (120 per minute, the same bucket as `POST /groups/{id}/events`). Over the limit: 429 `RATE_LIMITED`. There is no limit on the number of `code` and `userId` friends (one per person). `name` (placeholder friends) is limited to 200 per user: if there are already 200 friend groups where the caller is a non-removed member and the other member is not linked (not claimed yet, or the account was deleted), 409 `LIMIT_EXCEEDED` (a retry with the same `id` returns that group, as above). A claim frees a slot again.
- `code` and `userId` (A = the caller, B = the other person). One transaction:
  1. `SELECT id FROM users WHERE id IN (:a, :b) AND deleted_at IS NULL ORDER BY id FOR UPDATE` (concurrent requests from the two people line up). If it does not return 2 rows (an account was deleted while waiting for the lock), the same error as the lookup before (`code` 404, `userId` 403).
  2. If a `friendships(user_lo, user_hi)` row exists, return that group. The same two people always get the same group, whoever does it and however many times.
  3. Otherwise, insert a group row (`kind = 'friend'`, a new invite code) and store three server-made events **without validation** (trusted; the same lock, seq, apply and meta path): seq 1 `group.created {"name": "{A name} & {B name}", "defaultCurrency", "kind": "friend"}`, seq 2 `member.added {"memberId": new UUID, "name": A name, "userId": A}`, seq 3 `member.added {"memberId": new UUID, "name": B name, "userId": B}`. Names come from `users.display_name` (`Friend` if empty). The actor of all three events is A. Then insert (lo, hi, groupId) into `friendships`.
  4. Push **after** commit (`PushNotifier.notify`): B's devices get a `friend_added` visible notification and sync data (B's app does not know the groupId, so `syncAll()` takes in the new group).
- `user_lo` and `user_hi`: compare the two UUIDs as **lowercase strings**; the smaller one is lo (the same as the Postgres uuid order; Kotlin `UUID.compareTo` compares signed longs, so it is not used).
- `name`: made the same way, without the user lock and without a `friendships` row. seq 3 is `member.added {"memberId": new UUID, "name": name, "userId": null}`. The friend claims that placeholder with this group's invite code (`GroupDto.inviteCode`, `/j/{code}`). The `/j/{code}` landing page of a friend group shows "{name} added you as a friend on Evensies." with the linked member's name instead of the group name (`Someone` if there is none).
- The response is always 200 `GroupDto`. The app then takes in the group from the snapshot (same as joining by invite). Online only (expenses after the friendship exists work offline too).

**Friend group rules** (the validator looks at `state.kind`)
- Exactly 2 members. A third `member.added` gets 409 `LIMIT_EXCEEDED` (so `/invites/{code}/join {newMemberId}` on a friend group and new names from a Splitwise import get 409 too). `member.removed` gets 400 `VALIDATION` (no leaving; deleting a friend is phase 10).
- Claiming a placeholder friend (`/invites/{code}/join {memberId}` → `member.linked`) skips the group limit check. In the same request, `GroupService.join` inserts the `friendships` row for the two linked users with `ON CONFLICT DO NOTHING`. If the two people already had a friend group, both groups stay, and `POST /friends` keeps returning the group in `friendships`. The app merges friend groups with the same userId into one person.
- The name (`"Anna & Ben"`) shows only in exports (the app's export list shows `Non-group · Ben`). The app uses the other member's name. `group.updated` is accepted the same way as for regular groups, but the app has no settings screen for friend groups.
- Activity: seq 1 and 2 are hidden, and seq 3 is `friend_added` (see "Feed" below). The push title is the other person's name.

## Overview
Phase 6. One rule used by the Friends tab, the total card, the friend page and reminders. App `domain/overview.dart`, server `money/Overview.kt`; both read `shared/overview-cases.json` (each case goes state → `balancesOf`/`Balances.ofGroup` → `groupTransfers`/`Balances.transfers` → overview, so the Kotlin `Balances` port is checked too).

```
GroupLedger {
  groupId,
  myMemberId,                          // my member for new payments: my non-removed member, else my first member in state order
  personOf: {memberId: person},        // every member (mine included). linked → userId, placeholder in a friend group → "g:<groupId>", placeholder in a regular group → "m:<memberId>"
  transfers: {currency: [Transfer]}    // groupTransfers(state) (phase 4 buckets, unconverted buckets included): exactly what Settle up shows
}
Overview {
  people:   {person: {currency: amount}},             // + = that person owes me, − = I owe that person
  byGroup:  {person: {groupId: {currency: amount}}},
  owedToMe: {currency: amount}, iOwe: {currency: amount}
}
```
- `GroupLedger.of(groupId, state, myUserId)`: `null` if no member has `userId == myUserId` (phase 7: no group is left whose balances cannot be computed, so the `{n} group(s) not included yet` line is removed).
- `computeOverview(ledgers)`:
  1. My members = all members with `personOf[m] == myUserId` (removed included; a user who left and rejoined has two).
  2. For each transfer, `a = personOf[from]` and `b = personOf[to]`. If only `b` is me, `people[a][currency] += amount`. If only `a` is me, `people[b][currency] −= amount`. If both are me or neither is me, ignore it.
  3. Sum per person and currency (`people`) and per person, group and currency (`byGroup`). No conversion, no rounding.
  4. Remove zeros, then remove empty people and empty groups.
  5. `owedToMe[c]` = Σ max(0, people[p][c]), `iOwe[c]` = Σ max(0, −people[p][c]). If 0, the key is absent.
  6. Invariant (tested): per currency, `owedToMe[c] − iOwe[c]` = the sum of my members' balances across all ledgers.
- The design's (phase-06) "only my first member in state order counts as me" was pinned down as steps 1 and 2: looking only at the first member would drop the payments of a member who rejoined, and payments between my own two members would look like debts with me (`overview-cases` "left and rejoined").
- Server reminders compute with the same rules.
- Screens (app, English before the phase 9 translation):
  - People = the `personOf` values of all ledgers, except me. `m:` keys (placeholders in regular groups) show only when they are in `people` (have a balance), with that group's name as the subtitle. `g:` keys (placeholder friends) and linked users show even when settled (under Settled up). Name = that member's name in the friend group; otherwise the member's name in the first shared group in group name order. Route `/friends/:key` (`key` = userId, `g:<groupId>` or `m:<memberId>`).
  - Several friend groups with the same userId merge into one page, and a new non-group expense goes into the friend group with the smallest id (as a string). Adding an expense with a linked user who has no friend group first calls `POST /friends {userId, defaultCurrency: home currency}` (online only).
  - **Add expense** (set in phase 7): always shown if there is a friend group. Not shown for a placeholder in a regular group (`m:` key); add the expense in that group. For a linked user without a friend group, it shows only if there is a **group you are both in now** (a local `kind: "group"` group that has both a non-removed member linked to me and a non-removed member linked to that person; the same as the server condition of `POST /friends {userId}`). Otherwise, instead of the button, the page shows the line `You no longer share a group with {name}. Send them your friend link to add expenses.` and **Share friend link** (shares the link from `GET /me/friend-code` to the share sheet with the same text as the Add friend screen, `Add me on Evensies to split expenses: {link}\nOr enter my code {code}`; offline: `Sharing your friend link needs a connection.`). If the local state is behind and `POST /friends` gets 403 `FORBIDDEN`, the page shows the same line and button instead of the server error text. Tapping such a person in the home Add expense (picking *with whom?*) opens a dialog with the same text, **Share friend link** and Cancel.
  - Row: with one currency, `owes you €12.00` or `you owe $5.00`. With several, the largest one followed by `*`. "The largest" = the currency with the largest absolute value in EUR major units by the latest local rate table (phase 4 `FxDays`) (`|amount| / 10^digits / perEur[c]`, used only for sorting and not shown). Currencies without a rate go last; ties go by currency code.
  - The chips All · Owes me (> 0 in any currency) · I owe (< 0 in any currency) are the same in both tabs (people, and my balance in groups). People and groups that are 0 in every currency go under **Settled up (n)** (collapsed by default).
  - Total card (above both tabs): `You are owed €42.10 · $15.00` (`owedToMe`, in currency code order), `You owe €8.00` (`iOwe`), and `You are owed ≈ €61.20 in total` or `You owe ≈ €5.00 in total` (S = the sum over currencies of `convertAmount(owedToMe − iOwe, …, crossRate(latest table, c, H))` in home currency H. The sentence is picked by the sign of S, the amount is M(|S|, H), and no minus sign is used. Shown only when there are two or more currencies or the only currency is not H; hidden if any rate is missing or S = 0).
  - `overviewProvider` recomputes everything whenever local groups change (`ponytail:` full recompute; add a per-group cache if there are hundreds of groups).
  - Friend page: a header (photo, net per currency), a line per group (`byGroup`; tapping opens that group; the friend group line is `Non-group`), shared history (below), **Settle up** (see "Recording and editing payments" above), **Remind** (when a linked person owes me) or **Request** (for a placeholder), **Invite** for a placeholder friend (that group's `/j/` link), and CSV and JSON export of non-group expenses under More.
  - **Shared history** (phase 7, parity #109, Splitwise's friend screen): shows the expenses and payments of every local group shared with that person, in **sections per group** (app only, no server change). The groups are those that, by `personOf`, have both my member and that person's member (removed included). For friend groups, all non-deleted expenses and payments. For other groups, the non-deleted expenses where one of my members and one of that person's members each have a non-zero amount in `payers` or `shares`, and the non-deleted payments between my member and that person's member (either direction). ## Moving expenses
Phase 6. Changing *With* (a group or a friend) while editing moves the expense. Online only.
- `remapForMove(Expense e, List<Member> source, List<Member> target) → Expense?` (app, pure): each member in `payers` and `shares` with an amount above 0 (the people involved) is mapped to the non-removed member of the target group with the same `userId`. If anyone involved is a placeholder (no `userId`), or the target has no active member for that user, the result is `null` (app: `Only people on Evensies who are in both can be moved`). `payers` and `shares` entries that are 0 and `split.input` keys without a target member are dropped. `paidBy` is derived again as the main payer (rule 10). `fxRateToDefault` is kept only if both groups have the same default currency; otherwise `null`. After that, if the expense currency differs from the target's default currency and the rate is `null`, the edit screen fills in the automatic rate for that date (`GET /fx`), as for a new expense (`null` if there is none, so the expense is not converted in the target). Description, amount, currency, date, category, notes, refund and split mode stay as they are, and a new expenseId is made.
- Order: 1. Push that `expense.created` to the target group right away (not through the outbox). 2. Only after that succeeds, put `expense.deleted {"expenseId", "movedTo": {"groupId": target, "expenseId": new id}}` into the source group's outbox. If 1 fails, nothing changes (`Couldn't move it. Try again when you're online`).
- Retry (same target): reuse the `expenseId` and `clientId` from 1 (if the first try was stored and only the response was lost, the server sees a duplicate and returns its seq). In the same batch, add an `expense.updated` (with a new `clientId`) whose `fields` are all the current values of the expense (the `expense.created` payload without `expenseId`). If the first try was stored, edits made in between go in through this event; if not, the values are the same and the state does not change (activity hidden case 1).
- Comments and edit history stay on the original (deleted) expense. The activity is `expense_moved` in the source group (no Restore) and `expense_added` in the target group. The original expense becomes `moved` and is not restored (applier rule 13: even if an `expense.restored` that another device queued offline arrives later, the expense is not counted in two groups).
- If the target is a linked user who has no friend group yet, first call `POST /friends {userId}`.

No `file` part: 400 `VALIDATION`. Then `Jpeg.clean(bytes, 1024)`: if the data does not start with SOI (`FF D8`) or the structure is broken (a segment length runs past the end, the data is cut off, or there is no SOFn before SOS), 400 `NOT_JPEG`. If the SOFn width or height is over 1024, 400 `IMAGE_TOO_LARGE`. The server does not decode untrusted pixels (the app already re-encoded them). The Content-Type header is not checked.
- `Jpeg.clean` walks the markers, keeps APP0 and APP14, and drops APP1–APP13, APP15 and COM (EXIF and GPS, XMP, IPTC, embedded thumbnails). Other segments (DQT, DHT, SOFn, DRI, SOS…) stay. In the entropy-coded data after SOS, `FF 00` and `FF D0`–`FF D7` are data, and a run of `FF` before a marker is fill bytes. Progressive JPEG (several SOS) works too. It stops at EOI and drops any bytes after it. The result must decode to the same size (tested).
- Storage: `storage/FileStore.kt` `write(key, bytes)` (a temp file in the same directory → `Files.move(…, ATOMIC_MOVE)`), `path(key): Path?`, `delete(key)`. The root is `EVENSIES_STORAGE_DIR`. Keys are built only from UUIDs that Spring has already parsed (no path traversal): `avatars/{userId}.jpg`, phase 7 `attachments/{groupId}/{id}.jpg` and `{id}_thumb.jpg`, phase 10 `covers/{groupId}/{coverId}.jpg`. `ponytail:` local disk only. When the disk is about 70% full, propose S3-compatible storage along with its cost.
- Account deletion deletes `avatars/{userId}.jpg` after commit.
- App: tapping my photo in Settings offers Take photo / Choose from library / Remove. `data/images.dart` `prepareJpeg(XFile picked, {required int maxEdge, required int quality})` (applies the orientation to the pixels, removes EXIF, HEIC → JPEG; new dependencies `image_picker` and `flutter_image_compress`, iOS `NSCameraUsageDescription` and `NSPhotoLibraryUsageDescription`). Profile photos use `maxEdge: 512, quality: 85` (about 50 KB). `PersonAvatar(userId?, name)`: `BoxFit.cover` inside a circle; the name's initials if there is no photo or on error. `avatarProvider(userId)` fetches through `ApiClient` (token refresh) and remembers the photo for the session; my own photo is fetched again after I upload or remove it. `docs/privacy.md` has a profile photo entry (who sees it, a 512px JPEG on the server disk, deleted with the account).

## Receipts
Phase 7. Receipt photos are attached to expenses (up to 10 per expense). Only members of that group can download them. Text recognition (scanning) runs only on the phone; only the photos the user attaches go to the server. Storage uses the phase 6 `FileStore` (`EVENSIES_STORAGE_DIR`) and `Jpeg.clean`.

| Method | Path | Request | Response |
|---|---|---|---|
| POST | `/groups/{id}/attachments/{attachmentId}` | multipart `image` (JPEG, at most 2,097,152 bytes, width and height at most 4096px) + `thumb` (JPEG, at most 204,800 bytes, at most 1024px). `attachmentId` is a UUID made by the app | 201 `{"id": "<attachmentId>"}`. **Upload** check order:
1. No such group: 404 `NOT_FOUND`. The caller is not a current (not removed) member: 403 `FORBIDDEN` (`requireMember`).
2. Rate (abuse cap): 60 per hour per user (in-memory `RateLimiter(60.0, 60.0 / 3600)`, a different bucket from profile photos; failed attempts and 200 retries count too) → 429 `RATE_LIMITED`.
3. No `image` or `thumb` part → 400 `VALIDATION`.
4. Size: `image` > 2,097,152 bytes or `thumb` > 204,800 bytes → 413 `TOO_LARGE`. A request over the multipart limit (5 MB) gets 413 `TOO_LARGE`, as now.
5. Look up the `attachments` row: if it is this group's row (attached or deleted), 200, and no files are written (the first write wins, so retries are safe). If it is another group's row, 409 `DUPLICATE`.
6. `Jpeg.clean(image, 4096)`, `Jpeg.clean(thumb, 1024)` (the same function as in phase 6; it strips metadata and does not decode pixels) → 400 `NOT_JPEG` / 400 `IMAGE_TOO_LARGE`.
7. Write the two files `attachments/{groupId}/{attachmentId}.jpg` and `attachments/{groupId}/{attachmentId}_thumb.jpg` (`FileStore.write`), then insert the row (`expense_id = NULL`, `uploaded_by` = the caller). If the same id comes in at the same time and causes a `DuplicateKeyException`, check 5 again (200 for this group, 409 for another group). → 201.
- An uploaded row is attached to no expense and is not in the snapshot until `attachment.added` comes. The phase 8 daily cleanup ("Daily cleanup" in "Recurring expenses") deletes uploads (rows and files) that stayed unattached for 7 days, and the files of deleted rows left behind by a crash.

**Download**: no such group 404, not a member 403 (checked first). If this group has no such row (an unknown id or another group's id), the row is deleted (`deleted_at`), or the file is missing, 404 `NOT_FOUND`. Members of the same group can download an upload even before it is attached. Headers: `Content-Type: image/jpeg`, `Cache-Control: private, max-age=31536000, immutable` (the files of an id never change), `X-Content-Type-Options: nosniff`. Always through the API (Bearer token).

## Itemized split (app only)
Phase 7. The calculation for SplitSpec mode `itemized` (parity #6 and #7). The server does not recompute shares (see "SplitSpec" above), so there is no Kotlin twin. App `domain/itemized.dart`, fixture `app/test/fixtures/itemized-cases.json`.
- `itemizedTotal(bill)` = Σ `lines[].amount` + `tax` + `tip` − `discount`.
- `computeItemizedSplit(bill) → {memberId: share}`, errors are `SplitException(code)`:
  1. Any of line `amount`, `tax`, `tip` or `discount` < 0 → `NEGATIVE_AMOUNT` (checked first). A line with empty `memberIds` → `UNASSIGNED_ITEM`.
  2. First add up the `amount` of lines whose `memberIds` are the same set (order does not matter), then for each sum call `computeSplit(amount: sum, mode: equal, members: those members)` (the remainder goes +1 by ascending memberId). So three 1.00 lines shared by a, b and c give 1.00 to each of the three, not 1.02 to a (the same person does not get the remainder on every line). subtotal[m] = the sum of m's shares, S = Σ subtotal (= Σ line amount).
  3. net = tax + tip − discount, total = S + net. total < 0 → `NEGATIVE_TOTAL`. S == 0 and net ≠ 0 → `ZERO_SUBTOTAL`.
  4. Split |net|: base[m] = ⌊|net| × subtotal[m] / S⌋ (the product uses `BigInt`, so it is exact on the web too), r = |net| − Σ base, and +1 goes to the first r members by ascending memberId among members with subtotal > 0 (not by largest remaining fraction).
  5. share[m] = subtotal[m] + extra[m] if net ≥ 0, otherwise subtotal[m] − extra[m] (it never goes negative).
  6. The keys of the result are all members on any line (0 included), and the sum is `itemizedTotal(bill)`. Deterministic.
- `percentOf(subtotal, pct)` = `(subtotal × pct / 100).round()` (UI only, .5 rounds up). A % input for tax, tip or discount is stored as an amount (the bill holds only amounts).
- Form: the split method is 6 `ChoiceChip`s (Equal · Exact · % · Shares · ± · Items). With Items, the form shows a summary (`4 items · Anna €18.40 · Ben €22.80 · Edit`) and a read-only amount (`itemizedTotal`). Saving sends `split: {"mode": "itemized", "bill": …}` together with `shares` (= every key of `computeItemizedSplit`, 0 included), `amount` and the other money fields (phase 3 rule). Switching to another method uses that method's `split` (`null` for exact). Opening uses the comparison in "SplitSpec" above (Exact if it does not match). The item screen `features/itemize/itemize_screen.dart` follows the design (line name, amount, member chips and All; lines without people are highlighted and Done is blocked, plus `Give the rest to everyone`; amount/% toggle for tax, tip and discount; live totals per person; members who left but are already on a line show by name).
- Moving (`remapForMove`): maps `split.bill.lines[].memberIds` to target members, like shares. If any id cannot be mapped, `split` becomes `null` (shares are the source of truth, so the expense opens as Exact).
- The maintainer's `computeSplit` does not compute `itemized` (it only borrows equal). There are no per-line weights ("2 of 3 beers").

## Recurring expenses
Phase 8. The **server** adds repeating expenses such as rent, subscriptions and weekly cleaning. They show up on time even if nobody opens the app. A series is a group entity and travels as events (`recurrence.*`; see "Event types and payloads", "Recurring expense validation" and applier rules 15 and 16 above). Each occurrence the server adds is a normal `expense.created`, so balances, export, search and activity work as they are. Friend groups (phase 6) work the same way. No new endpoints and no new environment variables.

```
RecurrenceDto {"id","frequency": "weekly"|"biweekly"|"monthly"|"yearly","startDate": "YYYY-MM-DD","timeZone": string,"template": {...},"deleted": bool}
```

**template** = the `expense.created` payload the series will make, without `expenseId`, `date`, `recurrenceId` and `occurrence` (the received JSON as is; jsonb on the server). The phase 3 payers, refund and split hint (`split`, including the phase 7 itemized `bill`), phase 2 notes, phase 4 currency and rate, and phase 5 category come along with no migration. Occurrences use the template's `shares` and `payers` as they are: the server does not recompute splits (phase 3 principle), so itemized expenses also repeat with the stored shares. Receipts do not repeat (they are `attachment.added`, not a field of the expense).

**Dates** (server `recurrence/Schedule.kt`, app `domain/recurrence.dart`, `shared/recurrence-cases.json`):
- `occurrenceDate(frequency, startDate, n)`: weekly = startDate + 7n days, biweekly = + 14n days, monthly = + n months, yearly = + n years. A day that does not exist in that month becomes the last day of the month (1/31 → 2/28 → 3/31 → 4/30, 2/29 → 2/28 of the next year). **Always computed from startDate** (computing from the previous date would get stuck on the 28th after a 31st). n = 0 is startDate (the first expense of the series). Kotlin uses `plusDays`, `plusMonths` and `plusYears`; Dart uses only `DateTime.utc` and clamps to the last day of the month by hand (adding in local time shifts by a day at DST, and `DateTime(y, m + 1, 31)` overflows into the next month; the fixtures catch both).
- `firstOnOrAfter(frequency, startDate, date, minN = 1) → {n, date}` = the smallest n with n ≥ minN and `occurrenceDate(n) ≥ date` (the app name is `firstOccurrenceOnOrAfter`). It never returns 0 (minN ≥ 1).
- `dueAt(date, timeZone)` (server only) = the UTC time of **09:00** on that date in the series' `timeZone`: `ZonedDateTime.of(date, LocalTime.of(9, 0), ZoneId.of(timeZone)).toInstant()` (if that time falls in a DST gap, it is pushed later, per the `ZonedDateTime` rules).
- `timeZone`: the app sends the device's current offset `±HH:MM` (`core/ids.dart` `deviceTimeZone()` = `DateTime.now().timeZoneOffset`; UTC is `+00:00`; the web sends the browser's offset). IANA names cannot be had without a plugin (no new dependencies). So when DST changes, only the posting time moves by an hour; the date does not move. The server accepts anything `ZoneId.of` accepts (IANA names, `Z`, `±HH:MM` and so on). Each series has its creator's time zone, so there is no account time zone setting (parity #96).

**Server storage**: Flyway `V10__recurrences.sql` (the file's first comment names this section by its earlier Korean title; an applied migration can't be edited, because Flyway checksums the whole file):
```sql
-- Repeating expenses (Phase 8, docs/API.md "Recurring expenses").
CREATE TABLE recurrences (
    id              uuid PRIMARY KEY,
    group_id        uuid NOT NULL REFERENCES groups (id),
    frequency       text NOT NULL CHECK (frequency IN ('weekly', 'biweekly', 'monthly', 'yearly')),
    start_date      date NOT NULL,
    time_zone       text NOT NULL,
    template        jsonb NOT NULL,
    created_by      uuid REFERENCES users (id),
    created_at      timestamptz NOT NULL DEFAULT now(),
    deleted_at      timestamptz,
    next_occurrence int NOT NULL,          -- scheduler-owned, never sent to clients
    next_due_at     timestamptz NOT NULL   -- scheduler-owned
);
CREATE INDEX recurrences_group_id ON recurrences (group_id);
CREATE INDEX recurrences_due ON recurrences (next_due_at) WHERE deleted_at IS NULL;
ALTER TABLE expenses
    ADD COLUMN recurrence_id uuid REFERENCES recurrences (id),
    ADD COLUMN occurrence    int CHECK (occurrence >= 0),
    ADD CONSTRAINT expenses_series_pair CHECK ((recurrence_id IS NULL) = (occurrence IS NULL));
```
- `GroupState.recurrences: Map<String, RecurrenceDto>` (`RecurrenceDto(id, frequency, startDate, timeZone, template: JsonNode, deleted)`), `ExpenseDto.recurrenceId: String? = null` and `occurrence: Int? = null` (the defaults also read older `events.meta`). `SnapshotDto.recurrences`. `load` reads in `created_at, id` order.
- `GroupStateStore.persist(groupId, actorUserId: UUID?, state, type, payload, createdAt: Instant)`: for `recurrence.*`, the series as it is in the state after applying is written with `INSERT … ON CONFLICT (id) DO UPDATE SET template = EXCLUDED.template, deleted_at = CASE WHEN :deleted THEN COALESCE(recurrences.deleted_at, now()) ELSE NULL END WHERE recurrences.group_id = EXCLUDED.group_id` (0 rows means 400 `VALIDATION`, an id from another group; a series not in the state does nothing). The expense upsert also writes `recurrence_id` and `occurrence` (the series row goes in first in the same push, so the foreign key holds; normalization removes series from other groups and missing series).
- The scheduler columns are set only on the first insert (the `ON CONFLICT` above does not touch them): c = the `createdAt` of that `recurrence.created` event (the app's clock) clamped to [now − 30 days, now], `next_occurrence = firstOnOrAfter(frequency, startDate, LocalDate.ofInstant(c, ZoneId.of(timeZone))).n`, `next_due_at = dueAt(occurrenceDate(next_occurrence), timeZone)`. So a series created offline loses no occurrences in between if it syncs within 30 days (a `next_due_at` already in the past is posted on the next tick), and a wrong clock cannot pour out many occurrences at once. Dates before the creation day are not filled in (even if startDate was three months ago, the first occurrence comes after the creation day; the app's `Next:` line shows it). If 09:00 on the creation day has already passed, that occurrence is posted on the very next tick.
- The schedule (`frequency`, `startDate`, `timeZone`) and the scheduler columns never change through later events. To change the schedule, the app stops the old series and creates a new one (see "App" below). A stopped series is never restored.

**Posting** (`recurrence/RecurrenceScheduler.kt`: `@Scheduled(fixedDelay = 60_000) fun tick() = runDue(Instant.now())`, with `@EnableScheduling` on `EvensiesServerApplication`. No new dependencies):
1. `SELECT id, group_id FROM recurrences WHERE deleted_at IS NULL AND next_due_at <= :now ORDER BY next_due_at LIMIT 200`.
2. For each row, post one occurrence at a time while the next one is due (one occurrence = one transaction):
   1. Read the row without a lock: `n = next_occurrence`, `date = occurrenceDate(n)`. Get the rate table `FxService.rates(date)` **outside the group lock** (calling the source can take up to 10 seconds; with the phase 4 cache, it answers right away).
   2. Transaction: `groups.lockForUpdate(groupId)` → read the row again. If it is stopped, `next_due_at > now`, or `next_occurrence ≠ n` (another instance already posted it), this row is done.
   3. Use `oid = UUID.nameUUIDFromBytes(HmacSHA256(key = EVENSIES_JWT_SECRET, "evensies:recurrence:{id}:{n}".toByteArray(UTF_8)))` (id in lowercase form, `RecurrenceScheduler.derivedId`) as the clientId and the expenseId. Event = `expense.created`, payload = template + `{"expenseId": oid, "date": date, "recurrenceId": id, "occurrence": n}`, `createdAt` = the row's `next_due_at`.
   4. **Rate refresh**: D = the group's default currency, c = the template's `currency`, r = the template's `fxRateToDefault`. If c ≠ D, r is a number above 0, and the table from step 1 gives `crossRate(perEur, c, D)`, set the payload's `fxRateToDefault` to that value (the same value as the automatic rate for that day that the app fills in for a new expense: `perEur[D] / perEur[c]` to 6 significant digits, Kotlin `BigDecimal(x).round(MathContext(6, RoundingMode.HALF_UP)).toDouble()` = Dart `double.parse(x.toStringAsPrecision(6))`, `shared/recurrence-cases.json` kind=crossRate). Otherwise use the template value as is: `null` and `0` (the "Not converted" the user chose) stay, and with no table, the template's earlier rate is used. The template itself is not changed.
   5. `EventValidator.validateAll(state, actorUserId = null, [event])` (normalization included), then store through the push core (see "System actor" below). If the clientId already exists, skip without storing (idempotent).
   6. `next_occurrence = n + 1`, `next_due_at = dueAt(occurrenceDate(n + 1), timeZone)`. Commit.
   7. **After** commit, if new events were stored, `PushNotifier.notify(groupId, actorUserId = null, stored)`.
3. If validation or storing fails (possible only through a bug or a DB problem, such as a lock timeout or a lost connection, because the template was checked as an expense when it was stored), that transaction rolls back with a WARN log, and a new transaction does only `UPDATE recurrences SET next_due_at = now + 1 hour WHERE id = :id AND next_occurrence = :n` (n as read in step 1). That occurrence is delayed and the other series go on. If another instance moved n forward in the meantime, this updates 0 rows, so it does not overwrite the next due time that instance set.
- Safety: the group lock is taken first and the row is read again, so a stop or edit that arrives at the same time (a push that takes the same lock) is always seen. Crashes, retries and a second instance are stopped by `UNIQUE(group_id, client_id)`, since they use the same derived clientId. Occurrences missed while the server was down are all posted in order on the next tick (the 30-day clamp applies only when a series is first inserted).
- Only the server makes derived ids. The app cannot send an `occurrence` above 0, so two offline phones cannot create the same occurrence. The key is the server secret, so someone who knows the series id (former members included) cannot work out the next occurrence's id. Without the key, such a person could stop a series by putting an expense with that id into another group ahead of time (expense ids are a global PK, so the occurrence would fail with 400 and be delayed forever) or by inserting an event with that clientId (the occurrence would be skipped silently). Posting exactly once is guaranteed by the group lock, the row re-read and the advance in the same transaction; the derived id is only a backstop, so changing the secret is fine.
- `ponytail:` one `stateStore.load` per occurrence. If many occurrences need catching up, batch them per group.
- Tests use dates after 2031 so the real tick does not touch them, and call `runDue(Instant)` directly (even if the real tick posts first, the result is the same: one event per occurrence).

**System actor**: scheduler events have no user (`null` = Evensies). The push core of `EventService`, `GroupStateStore.persist`, `EventValidator.validateAll`, `Activity.meta` and `PushNotifier.notify` accept a `null` user. Stored events have `actor_user_id NULL` (pull: `"actorUserId": null`), and expense rows have `created_by NULL`. Member checks and the per-user rate limit (120 per minute) are skipped. The pulled `createdAt` is `dueAt`, and the activity's `createdAt` (`received_at`) is the time the event was actually stored. The activity is `expense_repeated` (see "Feed" below), and the push goes to all linked members (see "Push notifications" below).

**Daily cleanup** (`storage/Sweep.kt`, `@Scheduled(cron = "0 30 3 * * *")`, server clock; work left over from phase 7):
1. `DELETE FROM attachments WHERE expense_id IS NULL AND created_at < now() - interval '7 days' RETURNING id, group_id`: uploads not attached to any expense for 7 days (a rejected `attachment.added`, or the app went away after uploading). For each deleted row, delete both files (`AttachmentController.keys`). The row is deleted first, so nothing can attach to it in between (attached rows do not match the condition). Why 7 days: a phone that lost its connection between the upload and its `attachment.added` push should not lose the receipt even if it stays offline for days (an `attachment.added` after that gets 400 `ATTACHMENT_NOT_UPLOADED`).
2. Delete both files of rows that have `deleted_at` (files left behind by a crash between the commit and the file deletion; a missing file does nothing). `ponytail:` looks at every deleted row every day. If there are hundreds of thousands of rows, narrow it to the last 7 days.
- If a file deletion fails, only a WARN log is written (step 2 checks again the next day; files from step 1 stay as orphans; `ponytail:` if that becomes a problem, scan the directory). Phase 10: the same cleanup also deletes cover files that are not a group's current cover (files written within the last 1 hour are kept; see "Group types, covers and deletion").

**Limits**: 100 series that are not stopped per group (abuse cap, 409 `LIMIT_EXCEEDED`). Everything else is free and unlimited.

If it is not Never, `Next: Sun, 1 Nov 2026` (`DateFormat('EEE, d MMM yyyy')`, `firstOccurrenceOnOrAfter(frequency, startDate, todayIso(), minN: lastPosted + 1)`; for a new expense, startDate = the form's date and lastPosted = 0). The saved expense is the first one of the series (`occurrence: 0`).
  - The latest occurrence of an active series: an **Also change future repeats** checkbox (checked by default). On save:
    - Repeat → Never: `stopRecurrence` + `updateExpense` (if any field changed).
    - Repeat changed (whatever the checkbox says; the checkbox is hidden meanwhile), or the box is checked and the date changed: `repeatFrom(…, stop: old id)` (the schedule restarts from this expense). The checkbox only decides whether the date and fields carry forward when Repeat stays the same.
    - Checked, any other case: `updateExpense` + `updateRecurrence(the same changed fields without date)` (not sent if nothing is left).
    - Not checked: only `updateExpense`.
  - An occurrence of an active series that is not the latest: Repeat is disabled, with `To change future repeats, edit the latest one (1 Oct)` (`d MMM`, the date of the latest occurrence).
  - An expense with no series or with a stopped series: Repeat starts at Never; if the user picks one, `repeatFrom(…)` on save (no stop, a new series).
  - Delete on an expense of an active series: Cancel / Delete this one / **Delete and stop repeating** (`expense.deleted` + `recurrence.deleted`, one transaction).
- Expenses tab: `Icons.repeat` on expenses of active series.
- Expense detail: an expense of an active series shows `Repeats monthly` at the end of the date line (the same frequency words as the activity). For the latest occurrence, `· next Sun, 1 Nov 2026` (the same calculation as `Next:` above); if the template's amount or currency differs from this expense, `· next €1,300.00 on Sun, 1 Nov 2026`. **Phase 9**: uses the same words as the form and moves from the date line to its own line below it (`Icons.repeat`): `Repeats every month` (the same words as the form's Repeat options Every week / Every 2 weeks / Every month / Every year); for the latest occurrence, `Repeats every month · next on Sun, 1 Nov`; and if the amount or currency differs, `Repeats every month · next €1,300.00 on Sun, 1 Nov` (dates use `DateFormat.MMMEd(language)`; the next occurrence is always within 1 year). Three ARB sentences (the frequency through ICU `select`); fragments are not joined. The form's `Next:` line uses `DateFormat.yMMMEd(language)`.
- Members screen: removing a member who is in an active series' template (an amount above 0 in `payers` or `shares`) adds one line: `Ben is still in 2 repeating expenses (Rent, Netflix); they keep Ben's share until you edit the latest one.` (names in series creation order, up to 3, then `and N more`. Removed members are still members, so the server accepts this, and the occurrences keep creating that share).
- Moving (phase 6): `remapForMove` drops `recurrenceId` and `occurrence` (the new expense in the target has no series). The series stays in the original group.
- Offline: creating, editing and stopping work offline too. Only the server makes occurrences after the first (they arrive by pull after syncing).

**Left out on purpose**: filling in past dates on creation (the `Next:` line shows the first occurrence); custom intervals, end dates and weekdays only (Splitwise does not have them either); a "Repeating expenses" list screen; deleting occurrences posted before an offline stop reaches the server (that would mean trusting the device clock); and when two people both change one series' schedule offline, there will be two series (client-made derived ids would make local copies drift from the server). Email reminders before an occurrence (`remindDaysBefore`) are added by phase 10 on top of this scheduler.

### Building sentences
App `domain/activity.dart`, server `activity/ActivityText.kt`, cases `shared/activity-cases.json`.
Viewer `me`, name table `names`, language `lang` (the app uses the UI language, the server the receiver's language):
1. **Template key** = `kind`. Exceptions: `expense_added` and `expense_repeated` with `refund` use `expense_added_refund` and `expense_repeated_refund`; `comment_added` with a `paymentId` uses `comment_added_payment`; when the app list shows several receipts on one line (`count` ≥ 2), `receipts_added` and `receipts_removed`; phase 10: `group_deleted` and `group_restored` of a friend group (`kind == "friend"`) use `friend_deleted` and `friend_restored` (the friend group name `"Anna & Ben"` is internal and never shown; the app decides by that group's `kind`, and the server by the group of the push or summary). A kind that is not in `en` uses `unknown`.
2. **Variant**: subject = `actorMemberId` (but `memberId` for `member_joined` and `member_left`, and `fromMember` for `payment_added`). Object = `memberId` for `member_added`, `member_removed` and `friend_added`; `toMember` for `payment_added`; `fromMember` for `payment_confirmed` (none otherwise). If the subject is `me` and the `en` template has `self`, use `self`; otherwise, if the object is `me` and there is `you`, use `you`; otherwise `other`.
3. **Values**: `{A}` (actor), `{member}`, `{from}` and `{to}` (payment members) follow the name rule: `words.you` if `me`; `words.someone` if `null` or not in `names`; otherwise the name as is. `{name}` is the group name, `{description}` and `{text}` (`""` if missing), `{amount}` = M(`amount`, `currency`, `lang`), `{frequency}` = `words.frequency[frequency]` (unknown values as they are), `{changes}` (6), `{n}` (ASCII digits).
4. **Capitals**: if the template starts with a placeholder and its value came from `words.you` or `words.someone`, uppercase the first UTF-16 character (Dart `toUpperCase()`, Kotlin `uppercase()`). Member names stay as they are (even if the name is `someone`). Nothing changes in the middle of a sentence.
5. **Tail** (joined with `words.dot`): for `expense_added` and `expense_repeated`, `myDelta` < 0 → `suffix.owe` (`{amount}` = M(−myDelta)); > 0 → `suffix.getBack` if `refund`, otherwise `suffix.lent`; 0 or `null` → none. `payment_added` with `status == "sent"` → `suffix.waiting` (`you` if `toMember` is `me`, otherwise `other`; `{to}` is the value from 3). When the app list shows `myDelta` on its own line (`withDelta: false`), only that tail phrase goes on that line.
6. **`{changes}`**: build the labels in `changes[]` order and join them with `changes.joiner`. If nothing is left (empty `changes`), `changes.other`.
   - `group_updated`: `name` → `changes.name` (`{from}` and `{to}` as they are), `defaultCurrency` → `changes.currency`, `simplifyDebts` → `simplifyDebtsOn` if `to == true`, otherwise `simplifyDebtsOff`, `defaultSplit` → `defaultSplit`.
   - `expense_updated` and `recurrence_updated`: `description` → `changes.description`; `amount` → `changes.amount` (`{from}` = M(from, the `from` currency of the `currency` change if there is one, otherwise `currency`), `{to}` = M(to, `currency`)); `currency` → `changes.currency`; `fxRateToDefault` → `fxRateToDefault`; `paidBy` → `changes.paidBy` (name rule, no capitals); `payers` → `payers`; `refund` → `refundOn`/`refundOff`; `date` → `changes.date` (ISO as is); `category` → `categorySame` if the names of both sides are the same, otherwise `changes.category`, where the name is `categoryLabel(raw, lang)` (= `words.categoryOther` (`{parent}` = the parent name in that language) if the key of `resolveCategory(raw)` is `*.other`, otherwise `categories[key]`); `shares` → `split` only if there is no `amount` change; `split` → `split` only if there are no `amount` or `shares` changes; `notes` → `notes`.
   - An unknown field adds `changes.other` only once (before: the server showed the field name and the app left it out. The server sends only fields it knows, so this shows only when a new server meets an older app).
7. **Grouped pushes** (server; the leave-out and grouping rules of "Push notifications" stay as they are): for 1 event, that sentence; if the actors are mixed, `batch.mixed`; all `expense_added` → `batch.expenses`; all `comment_added` → `batch.comments`; all `expense_repeated` → `batch.repeats`; otherwise `batch.changes`. `{A}` follows rules 3 and 4.

### Money notation M(x)
App `formatMoney`, server `Money.display`, cases `money` in `activity-cases.json`.
`M(minor, currency, lang)`, `L` = that language in `strings.json` (`en` for missing languages and keys):
1. d = `currencies.json` `decimals[currency]` (2 if missing). Split |minor| at d digits. Group the integer part in groups of 3 digits from the right with `L.money.group`, and if d > 0, add `L.money.decimal` and the fraction (d digits, zero-padded).
2. Symbol s = `L.money.symbols[currency]` → `currencies.json` `symbols[currency]` → the ISO code.
3. Replace `{s}` and `{n}` in `L.money.pattern` in one pass. If the pattern is `{s}{n}` and the last character of s is a Latin letter (`A–Z`, `a–z`, U+00C0–U+024F except U+00D7 `×` and U+00F7 `÷`), put U+00A0 between them.
4. A negative number gets a leading `−` (U+2212, the sign the app already uses; this is how the design's `-` was pinned down): `−€48.00`, `−48,00 €`. Shared sentences and server text never have negative numbers.

| Language | pattern | group | decimal | EUR 123456 |
|---|---|---|---|---|
| en, ko, ja, th | `{s}{n}` | `,` | `.` | `€1,234.56` |
| id | `{s}{n}` | `.` | `,` | `€1.234,56` |
| nl, pt | `{s}␣{n}` | `.` | `,` | `€ 1.234,56` |
| de, it, es | `{n}␣{s}` | `.` | `,` | `1.234,56 €` |
| fr | `{n}␣{s}` | U+202F | `,` | `1 234,56 €` |
| pl, sv | `{n}␣{s}` | U+00A0 | `,` | `1 234,56 €` |

␣ = U+00A0. The only per-language `symbols` entry is sv's `{"SEK": "kr"}`. Symbols that several currencies used to share were taken out of `symbols` in `currencies.json`: CAD `CA$`, AUD `A$`, SGD `S$`, HKD `HK$`, MXN `MX$`, CNY `CN¥`; SEK, NOK, DKK, ISK, KWD, BHD, AED and CLP were dropped from the table and use the ISO code (USD `$` and JPY `¥` stay). Examples: en `CA$12.34`, `CHF 12.50`, `RM 12.50`, `PYG 1,234`, `KWD 1,234.567`; sv `999,00 kr`, `12,50 NOK`; pt `R$ 1.234,56`; id `Rp 123.456`; ko `₩15,000`.
- The app no longer uses intl `NumberFormat.simpleCurrency`. `formatMoney(minor, currency, {String? lang})` (default `Money.lang`). Screens, activity, widgets and pushes all use the same notation. `plainAmount` (amounts in URLs, EPC QR) always uses `.` and no grouping (unchanged from phase 1).

### Amount input (app only)
`parseMoney(text, currency, {lang})` → an integer in minor units, or `null` (today `12,50` is silently stored as €1,250.00, and a `1,08` rate disappears):
1. Remove whitespace (U+00A0 and U+202F included), `'` and `’`, then remove everything except digits, `.`, `,` and a leading `-`. If nothing or only `-` is left, `null`.
2. No separator → whole units.
3. c = the last separator, k = the number of digits after it, D = the language's `money.decimal`, d = the currency's digits. `c == D` → decimal point (`null` if k > d). `c ≠ D` and k == 3 → grouping, no decimals (`null` if D appears anywhere). Otherwise → decimal point (lenient; `null` if k > d).
4. If the same character appears again before the decimal point, `null`. Other separators are dropped.
- `money_input_test.dart`: de EUR `1.234,56` → 123456, `12,5` → 1250, `12.50` → 1250, `12.345` → 1234500, `12,` → 1200, `-10,00` → −1000 (adjustment); en EUR `1,234.56` → 123456, `12.345` → `null`, `1.2.3` → `null`; fr EUR `1 234,56` (U+202F) → 123456; en KRW `1,234` → 1234; ko KRW `12.3` → `null`; en KWD `1,234` → 1234000; de KWD `1,234` → 1234.
- `parseDecimal(text)` (percentages, rates, share counts): the last separator is the decimal point, the other kind is grouping, and the same kind appearing again gives `null` (`1,0842` → 1.0842, `33,33` → 33.33).
- `inputAmount(minor, currency, {lang})`: the language's decimal point, no grouping (prefill, hints, **Copy amount**: de `12,50`). UI code never uses `toStringAsFixed` or a number's `toString()` (`hardcoded_strings_test.dart` looks for them).

### Home screen widget (app only)
iOS small and medium, Android 2×2.
Dart writes one JSON that is already translated and formatted, and the native code (Swift `EvensiesWidget`, Kotlin `BalanceWidgetProvider` + `org.json`) only draws it. `home_widget` 0.9.3, key `summary` (iOS App Group `group.dev.nariinfo.evensies`, Android home_widget prefs).
```json
{"v": 1,
 "lines": [{"text": "You are owed", "amount": "€42.10", "tone": "owed"},
           {"text": "You owe", "amount": "₩12,000", "tone": "owe"}],
 "empty": null,
 "updated": "Updated 11 Oct, 10:42"}
```
- `lines`: from the phase 6 `Overview`, net per currency = `owedToMe[c] − iOwe[c]`, with zeros dropped. `tone` is `owed` if net > 0 and `owe` if net < 0, and `amount` = M(|net|, c). Sorted like "the largest" in Friends rows (|net| converted to EUR major units with the latest local rate table, descending; currencies without a rate last; ties by currency code). At most 4 lines (2 in the small size; `…` on overflow).
- With two or more currencies and a rate to home currency H for every one of them (the same calculation as the phase 4 "≈"), one line instead: sum = Σ `convertAmount(net, …, crossRate(latest table, c, H))`, `amount` = `≈ ` + M(|sum|, H), and `tone` from the sign of the sum. If the sum is 0, use the per-currency lines.
- Signed out: `lines: []`, `empty` = `Sign in to see your balance`. Every net is 0: `lines: []`, `empty` = `All settled up`. If nothing was ever written, the widget shows only `Evensies`.
- The text comes from the UI language's ARB; `updated` is `Updated {DateFormat.MMMd + time}`.
- When it is written: when the overview or the UI language changes, with a 1-second debounce; nothing is written if the content is the same. Then `HomeWidget.updateWidget(iOSName: 'EvensiesWidget', androidName: 'BalanceWidgetProvider')`. Sign-out and account deletion write the signed-out payload. No background refresh. The web does nothing.
- iOS: Widget Extension (iOS 17; the app stays at 15.5), timeline `.never`, `.privacySensitive()` (hides amounts on the lock screen), teal = owed, red = owe. Android: `balance_widget.xml` (title, 3 lines, updated), `balance_widget_info.xml` (2×2, resizable, `updatePeriodMillis="0"`), `values-night` colors, and a tap opens `HomeWidgetLaunchIntent.getActivity`. The device's widget storage holds a copy of the balances (`docs/privacy.md`).
- The design's "`l.notImplemented` if `balancesOf` is null" and the `tryCore` fallback are gone: from phase 7 on, `balancesOf` always returns a value, and `tryCore` was removed.

With no saved answer and no server, or on an older server, the app reads `{emailLogin: false, appleLogin: true, googleLogin: true, reviewLogin: false}`, and the sign-in screen hides the buttons the server cannot handle.
- `UserDto.email`: the verified account address (never shown to other members anywhere). `emailBounced`: that address is blocked because of a `bounce` (app: "Emails to this address bounce — change it or verify it again"). The app reads a response without the keys as `null` and `false`.
- `GroupDto`, `GroupSummaryDto` and the snapshot's `group`: `type` (default `"other"`), `coverImageId` (default `null`), `deleted` (default `false`). The app reads a response without the keys as the defaults.
- `AccountExport`: snapshots of every group where the caller is a current (not removed) member (deleted groups and friend groups included). `notifications` is the same as `GET /me/notifications`. Receipt images come only in the per-group ZIP (phase 7). 3 per hour per user (abuse cap; 429 beyond that).
- `POST /me/logout-all`: deletes all of that user's refresh tokens and device rows (push to those devices stops too). `ponytail:` access tokens stay valid for up to 15 more minutes. If they must stop at once, check `users.tokens_valid_after` in `JwtAuthFilter`.
- `DELETE /me` (what phase 10 adds): sets `display_name = ''` and `email = NULL`, and deletes `notification_prefs`, `email_codes` (requested by that user or sent to that address), the `email_invites` that user sent, and `user_blocks` (both directions). An email-code account comes back as now (without a name) when someone signs in again with the same address.
- `notificationsAllowed` in `POST /devices`: whether the OS lets this device show notifications. The app sends it when it registers, and again when it comes to the foreground if the value changed. The "Auto" summary email uses it.

### Email validation
- Address: trim whitespace and lowercase it. At most 254 characters, `^[^\s@]{1,64}@[a-z0-9-]+(\.[a-z0-9-]+)+$` (no SMTPUTF8). An address of this shape that JavaMail cannot read as one address (`a,b@example.com`, `a"b@example.com`) is also 400 `VALIDATION` and is not written to `email_log`.
- Code: `^\d{6}$`.
- `remindDaysBefore`: an integer 1–7 or `null`, otherwise 400 `VALIDATION`.
- Group `type`: one of `trip`, `home`, `couple`, `other`. An explicit `type: null` is 400 too (because it would read as "unchanged").

### Email sign-in
`/auth/email/*`, covered by the permitAll on `/auth/**`.
- `start`: a 6-digit `SecureRandom` code, valid for 10 minutes, 5 attempts, single use. A new code replaces the previous one. Only `HMAC(K, email + ":" + code)` is stored (see "Tokens" below). The email is in the language of the active account that has that address, otherwise in English.
- `verify`: the active user with that `email`; if there is none, `findOrCreate("email", email, "")` and then `email` is set. A new user has an empty name, so the name entry screen appears. A deleted email account with the same address comes back (without a name). On success, the suppression for that address is removed (the address has been shown to work again).
- The comparison is constant time. Every attempt increments `attempts` (wrong attempts are committed too), and the sixth attempt fails whatever it is. A correct code deletes the row, so only one of several concurrent checks of the same code wins.
- If an Apple/Google account has the same verified address, sign-in goes to that account (see "Account email" below). Accounts are never merged automatically.

### Account email
- `IdTokenVerifier` gives `email` only when `email_verified` is true (Apple also sends it as the string `"true"`).
- Apple/Google sign-in: `users.email` is set only if the account has no address, the user never removed the address from that account (`users.email_removed`, V13), and no other active account has that address. A unique index race is caught and ignored (accounts are never merged automatically).
- Changing it (`POST /me/email` → `POST /me/email/verify`): the code goes to the new address. If another active account has that address, 409 `EMAIL_TAKEN`, but only at verify (start does not reveal it). For an email-code account, `subject` follows the new address too, so the old address no longer signs in to this account (signing in with the old address makes a new account). A **deleted** email-code account that used the same address gives it up (`:deleted:{id}` is appended to its `subject`). If no active account has the address, the address is free. When verify succeeds, the suppression for that address is removed.
- Removing it (`DELETE /me/email`): only for Apple, Google and dev accounts. `email = NULL` and `email_removed = true` (the next Apple/Google sign-in does not set the address from the id token again; adding one back with a code works). Without an address, there are no summary emails and no recurring expense reminders.

### Mailer
`email/Mailer.kt`, `JavaMailSender`.
- `EmailConfig` creates `JavaMailSenderImpl` only when `evensies.email.smtp-host` is not empty (not `spring.mail.host`: Boot treats an empty value as set). TLS: `starttls` (default, required), `ssl` (465), `none` (Mailpit only). Connect, read and write timeouts of 10 seconds. `/actuator/health` does not check the mail server.
- The order in `send(kind, to, chargedUserId, Email, ref?)`: 1. suppression (skipped for codes) → `SUPPRESSED` 2. daily budget → `OVER_BUDGET` 3. recipient address check (above) 4. an `email_log` row (the address is hashed) 5. send, and on success write `ref` to that row.
- A synchronous 5xx rejection (`SendFailedException.invalidAddresses`) → a `bounce` suppression + 400 `EMAIL_REJECTED`. Any other failure → 503 `EMAIL_UNAVAILABLE` (failed attempts stay in `email_log` too and count toward the budget and the per-address limits).
- Every email has `Auto-Submitted: auto-generated`. Invites, summaries and recurring expense reminders have `List-Unsubscribe: <url>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058). Code emails do not.
- CR/LF in user text is removed. Names are cut to 40 characters and comments to 80 (`…`).
- From: `EVENSIES_EMAIL_FROM`.

### Tokens
`email/EmailTokens.kt`.
- `K = HMAC-SHA256(EVENSIES_JWT_SECRET, "evensies-email")` (no new secret).
- Code hash: the hex of `HMAC(K, email + ":" + code)`.
- Unsubscribe token: `base64url("{kind}:{subject}") + "." + base64url(first 16 bytes of HMAC(K, the same text))`. kind `digest` (subject = userId; recurring expense reminders use this one too) or `invites` (subject = the sha256 hex of the address). No expiry. If the JWT secret changes, old links lead to a "change your settings in the app" page.

### Email invites
- The caller is an active member, and the member is in that group and is neither removed nor linked (linked: 409 `MEMBER_TAKEN`; missing, removed or in another group: 404; group deleted: 404).
- **204 without sending** (reveals nothing): the address is suppressed, that member already has an invite row, or the address got 3 invites in 7 days.
- 20 per inviter per 24 hours (invites + invite reminders) → 429. Daily budget at 100% → 429 "Email limit reached for today — share the link instead".
- An `email_invites` row is inserted only when an email was actually sent. People who already use Evensies are not linked automatically either (they pick the placeholder themselves).
- Language: that of the active account with that address, otherwise the inviter's.
- Link: `{EVENSIES_PUBLIC_URL}/j/{code}?m={memberId}`. `/j/{code}` passes `m` on to `evensies://join/{code}?m=…` and `/app/#/join/{code}?m=…` only if it is shaped like a UUID, and drops any other value. The app preselects that placeholder only if it is not linked yet, and the user confirms.

### Hourly job
`email/EmailJobs.kt`, `@Scheduled(cron = "0 5 * * * *")`, `evensies.email.job-cron`.
Does nothing if email is off. Order: cleanup → invite reminders → recurring expense reminders → summary emails. If one step fails, it only logs and moves on to the next step. `ponytail:` one instance reads every summary candidate every hour. With 10,000 users or two or more instances, read them in slices by due time and take `pg_try_advisory_lock`.
- **Cleanup:** expired `email_codes`, `email_invites` older than 14 days, `email_log` older than 30 days.
- **Invite reminders:** rows with `reminded_at IS NULL` and `sent_at` more than 3 days ago, where the member is still not linked and not removed, and the group is not deleted. Once per row. On hitting the budget, stop and continue on the next run.
- **Recurring expense reminders:** non-stopped series in non-deleted groups that have `remind_days_before`, with `reminded_occurrence < next_occurrence` and `next_due_at − remind_days_before days <= now < next_due_at`. Sent to the linked, non-removed members in the template's `payers` or `shares` who have an address, are not suppressed, have `email_digest <> 'off'`, and have not blocked the creator of the series. Once it has been sent to everyone (suppression counts as done) or if there is nobody to send to, `reminded_occurrence = next_occurrence`. If a send fails, that occurrence stays open and the next run tries again, skipping people who already got it (`email_log.ref = "{recurrenceId}:{occurrence}"`, V13). Stops on hitting the budget. "Your share" is the share stored in the template (the maintainer's function is not used). The last line of the email the series' creator gets is `email.recurring.footerSelf` ("…because you turned on reminders…").
- **Summary emails:** below.

### Summary emails
Settings → Notifications → Email summary.
- `emailDigest`: `auto` (default) · `daily` · `weekly` · `monthly` · `off`. Optional in PUT (if missing, the stored value stays); any other value is 400 `VALIDATION`. A change restarts the clock (from now on; events up to now are not sent).
- `emailDigestEffective` (read-only): `off` if there is no address, the server's email is off, the address is suppressed, or `emailDigest` is `off`. `auto` means `monthly` if there is a device that can receive push, otherwise `daily`. In all other cases, the chosen value. Can receive push = there is a device with an FCM token and `notificationsAllowed` that was seen within 60 days, and FCM is configured. If all three phase 2 push switches are off, it counts as no push.
- **Candidates:** active users with an address, not suppressed, with `email_digest <> 'off'`. If there is no `notification_prefs` row (or no clock), create it with `last_digest_at = now` and the current largest `feed_id`, and send nothing (the clock starts).
- **When:** `nextDue(last, mode)`: daily is the next 17:00 UTC, weekly the next Monday 17:00 UTC, monthly the next 1st of the month 09:00 UTC. Send if `now >= nextDue` (missed runs catch up). `ponytail:` UTC only (phase 8 has a time zone per series, not per user). Add `users.time_zone` if it is wanted.
- **Window:** events with `feed_id > last_digest_feed_id` (the global storage order from phase 2), in groups where that user is an active linked member, where the actor ≠ that user, and the actor is not blocked by that user. At most 500 at a time.
- **Lines:** phase 9 sentences (in that user's language); kinds without a sentence are left out. For an expense created and deleted within the window, every line about it is left out. A group that is deleted at send time gives only the `group_deleted` line from the window. 10 lines per group, 30 in total; beyond that, "…and N more in {group}". Groups go by latest event. Friend groups are called by the other person's name, and their delete and restore sentences are `friend_deleted` and `friend_restored` (see "Activity and notifications" below).
- **Balances:** `Balances.ofGroup(state)` (phase 6, per currency bucket). One line per non-zero balance per group and currency. On `NotImplementedError` (before the Kotlin port of the maintainer's function), only the balance part is left out. Balances of deleted groups are not included.
- **Send condition:** daily and weekly need at least one line; monthly needs at least one line or a non-zero balance.
- **After a run:** if the email was sent or there was nothing to send, `last_digest_at = now` and `last_digest_feed_id` = the largest value of that run. If the budget was hit or the send failed, they stay as they are.
- Summaries stop at 80% of the daily budget.

### Unsubscribes and bounces
`email/EmailController.kt`. `/email/unsubscribe` and `/webhooks/email` are permitAll.
- **GET** shows HTML shaped like a landing page (language from `Accept-Language`, `unsubscribe.*` in `strings.json`) with one button. Link scanners open the link ahead of time, so GET changes nothing.
- **POST** (the button, or the mail app's one-click) applies it: `digest` → `email_digest = 'off'` (summaries and recurring expense reminders stop; deleted accounts are skipped), `invites` → an `unsubscribe` suppression.
- The **webhook** `POST /webhooks/email` checks Resend's Svix signature: signed content = `svix-id + "." + svix-timestamp + "." + body`, key = the base64 after `whsec_`, the header holds space-separated `v1,<sig>` entries, and the timestamp must be within 5 minutes. `email.bounced` → a `bounce` suppression for each address in `data.to`; `email.complained` → a `complaint` suppression + `email_digest = 'off'` for the account with that address. Other types are ignored with 204. A suppression keeps its first reason (an unsubscribe does not turn into a bounce).
- Asynchronous bounces from other mail servers are not received (only synchronous 5xx).

### Daily budget and rate limits
These are abuse caps, not product limits.
| What | Limit | Over the limit |
|---|---|---|
| `/auth/email/start`, `/auth/email/verify` | 10 per minute per client IP (its own `RateLimiter`, `evensies.email.auth-rate-per-minute`) | 429 `RATE_LIMITED` |

### Group types, covers and deletion
Applier rule 17.
- **Types:** the `type` of `group.created` and `POST /groups` (`"other"` if missing), and `group.updated.type`. The app shows Trip `flight_takeoff`, Home `home_outlined`, Couple `favorite_border` and Other `groups_outlined`, each with its color band, and shows unknown values as Other.
- **Covers:** `PUT /groups/{id}/cover` → `Jpeg.clean(bytes, 2048)` (phase 6; removes GPS EXIF and so on) → `FileStore.write("covers/{groupId}/{coverId}.jpg")` → a `group.updated {"coverImageId"}` as the caller, inserted with `pushValidated` (if the push fails, the file is deleted). After commit, the previous file is deleted. A `group.updated` sent by a client can only have `coverImageId: null` (clear). A non-`null` value is 400 `VALIDATION` (the value is always made by `PUT /groups/{id}/cover`). Clearing with `null` deletes the file after commit. Uploading to a deleted group works too (it is accepted like other events).
- Cover `GET` is for members only (otherwise 403; no such group 404), and only for the current `coverImageId` (an old or unknown id gets 404). `Cache-Control: private, max-age=31536000, immutable`, `X-Content-Type-Options: nosniff`. The app caches it at `{appSupport}/covers/{coverId}.jpg` (an id's file never changes) and deletes the old file when the id changes.
- The phase 8 daily cleanup (03:30) also deletes cover files that are not a group's current id. Files written within the last 1 hour are kept (an upload writes the file before its `group.updated` commits).
- **Delete and restore:** `group.deleted {}` and `group.restored {}`, by any active member of the group (no admins). The group is deleted for everyone. `GroupStateStore` writes `deleted_at` (`COALESCE(deleted_at, now())` on delete, `NULL` on restore). Events after the delete are **not rejected** and are applied as usual (offline edits are not lost). Receipt and cover files stay.
- Deleted groups: no visible pushes and no summary lines except `group_deleted` and `group_restored` (data-only syncs still go out). Invite preview, join and landing give 404. The per-user group limit (100) counts only non-deleted `kind = 'group'` groups, so a restore is never blocked by the limit. Deleted groups drop out of reminder amounts (phase 6) (the app's overview and Friends tab leave them out too).
- Phase 8 scheduler: `runDue` skips series in deleted groups. When `group.restored` is applied (to a group that was deleted), the `next_occurrence` of each non-stopped series moves to the first occurrence from today on in its time zone (`firstOnOrAfter`, never backward). Occurrences from the time the group was deleted are not posted all at once.
- **Deleting a friend:** the app sends `group.deleted` for each friend group with that person. The non-group expenses disappear for both people and are restored the same way. A `POST /friends` by either of the two people adds a server-made `group.restored` (actor = the caller) to the deleted friend group and returns that group (the history comes back).
- App: Settings → Deleted groups (only when there are some) with **Restore**, a 10-second **Undo** right after deleting, and **Restore** on the `group_deleted` row in the activity. drift `Groups.type`, `coverImageId` and `deleted` (schemaVersion 10). `watchGroups` leaves out deleted groups, and they also drop out of the Friends tab, the total card, search and the widget.

### Blocking
Stored in `user_blocks`.
For the person who blocks:
- `POST /friends` from the blocked person → 404 for `code`, 403 for `userId` (the same as for an unknown person).
- A reminder from the blocked person → 200 for the sender, no push for the receiver.
- Events from the blocked person → no visible push (data only), no summary lines.
- No recurring expense reminders for series the blocked person created.

Money stays visible: shared groups and balances do not change (blocking only silences the person). **Report…** makes the app open `mailto:{supportEmail}?subject=Evensies report&body=User id: {userId}` (hidden if there is no `supportEmail`).

## Export and import
- `GET /groups/{id}/export?format=json` → the same JSON as the snapshot (`payers`, `refund`, `split`, `simplifyDebts` and `defaultSplit` included). `format=csv` → an expense CSV (`date,description,category,amount,currency,fxRateToDefault,paidBy,<share per member name>...`). The `category` column (phase 5) holds the English label for a key (`Categories.label`, e.g. `Dining out`; `*.other` is `Entertainment - Other`), `General` for `null` or whitespace only, and the original text for anything else (older free text). The `fxRateToDefault` column (phase 4) writes the stored value as a decimal without exponent notation or trailing zeros (`BigDecimal.valueOf(r).stripTrailingZeros().toPlainString()`: `0.00616`, `0.0000007`, `1.0` → `1`, `0` → `0`), and is empty for `null` (0 and values left on D expenses are written as stored too). Amounts are in the expense currency, as now (not converted). The `paidBy` column is the name for one payer, or `Anna 60.00; Ben 40.00` for several (in `payers` order, amounts in major units). Refund rows have negative `amount` and share columns (`-60.00`), while the amounts in the `paidBy` column stay positive. Text cells (member name headers, `description`, `category`, `paidBy`) that start with `=`, `+`, `-`, `@`, a tab or CR get a leading `'` (this stops spreadsheet formulas from running: CSV injection). Amount cells stay as they are.
- `GET /groups/{id}/export?format=zip` (phase 7, `ZIP with receipts` in Settings → Export) → 200 `application/zip`, `Content-Disposition: attachment; filename="evensies-{id}.zip"`. Entries: `group.json` (= the body of `format=json`, `attachments` included) and `receipts/{attachmentId}.jpg` for each non-deleted receipt (the full photo; included even if its expense is deleted; skipped if the file is missing). It is a `ZipOutputStream` that writes straight to the response stream on the request thread (the async dispatch of `StreamingResponseBody` gets cut off with 403, because the stateless JWT filter does not authenticate it again), and the member checks (404, 403) run before writing, so they answer with normal error bodies. A `format` other than `json`, `csv` or `zip` is 400 `VALIDATION`. CSV and JSON do not change (JSON only gains `attachments` and `replaced`). Phase 8: the JSON (and so the ZIP's `group.json`) gains `recurrences` and the expenses' `recurrenceId` and `occurrence` (= snapshot). CSV is unchanged (occurrences are normal expense rows too).
- `POST /groups/{id}/import/splitwise` multipart `file` (Splitwise CSV: `Date,Description,Category,Cost,Currency,<name>...`). The server matches names to group members (creating placeholder members for names it cannot match) and converts rows to `expense.created` events. Response `{"imported": n, "latestSeq"}`.
  - A name column is that person's net in that row (paid − owed). Everyone with a positive net pays that net. The person with the largest net (on a tie, the smallest memberId) also pays the remainder `s = Cost − Σ positive nets` and owes `Cost − Σ others' owed amounts` (this equals `s` when the nets sum to 0; for rows whose nets do not sum to 0, the shares still add up to Cost). A person with a negative net owes `−net`. If `s < 0` or that owed amount is negative, 400 `IMPORT_FAILED`. Payers and shares of 0 are not included. With two or more payers, `payers` is included (`paidBy` is the main payer). Example: Cost 100.00, Anna +26.66, Ben +6.67, Cara −33.33 → payers Anna 93.33 and Ben 6.67, shares Cara 33.33 and Anna 66.67. A row with one positive net comes in as now. Refund rows with a negative Cost are not imported yet.
  - The `Category` column (phase 5): if `Categories.keyForLabel` of the trimmed value (see "Categories" above) gives a key, that key; otherwise the trimmed original text (an empty or missing column is `null`). `Dining out` → `food.dining_out`, `General` → `uncategorized.general`, `Entertainment - Other` → `entertainment.other`, `Other` and `Food` → the original text as is.
  - Payment rows (phase 5): if `Category` is `Payment` (case-insensitive), Cost > 0, exactly two people have a non-zero net, and those nets are +Cost and −Cost, the server creates `payment.created {"paymentId": new UUID, "fromMember": the member whose net is +Cost, "toMember": the member whose net is −Cost, "amount": Cost, "currency": the row's Currency, "date": the row's Date, "status": "confirmed"}` instead of an expense (the balance effect is the same as importing the row as an expense). Payment rows that do not meet these conditions are imported as expenses, as now (with the original text `Payment` as the category).
  - `imported` in the response = the number of expenses created + the number of payments (phase 5). Member events are not counted. The response shape is unchanged.

## Activity and notifications
The **activity feed** built from the change history (the event log), **visible push** notifications about other people's changes, and notification settings. Feed items are structured data, and the app (list) and the server (push) build the sentences by the same rules (see "Activity sentences" below; both sides are checked with `shared/activity-cases.json`).

### Feed
| Method | Path | Request | Response |
|---|---|---|---|
| GET | `/groups/{id}/activity?before=<seq>&limit=50&expenseId=<uuid>` | `expenseId` is optional (phase 5) | `ActivityPage`, highest seq first. The caller must be a member (403); no such group 404 |
| GET | `/activity?before=<feedId>&limit=50` | | `ActivityPage` for all groups where the caller is a current (not removed) member, highest feedId first |

```
ActivityItem {"groupId","feedId","seq","kind","createdAt","actorMemberId",

```
- `expenseId` (phase 5, an expense's edit history): only events whose payload `expenseId` string equals that value (`expense.*`, `comment.added`, phase 7 `attachment.*`; for `attachment.deleted`, the `expenseId` the server added by normalization, see "Event types and payloads" above). Not a UUID → 400 `VALIDATION`. An empty value (`expenseId=`) counts as absent (no filter, the same as for `limit` and the others). The comparison is on the string as is, and the parameter is lowercased before comparing (the app makes ids in lowercase). For an expense that is not in the group (including one not pushed yet), the answer is an empty page `{"items": [], "nextBefore": null}`, not 404. `before`, `limit`, `nextBefore` and the hiding rules are unchanged, and `limit` counts filtered events (SQL `AND payload->>'expenseId' = :expenseId`). It is not available on `GET /activity` (the full feed; ignored if sent). `ponytail:` scans the group's events. When a group passes about 50,000 events, add an expression index on `(group_id, (payload->>'expenseId'))`.
- The app's History (expense detail): `limit=20`, and "Show more" uses `before=nextBefore`. Received items also go into the activity cache (drift `Activity`). If offline or on error, it shows that group's cache rows with `json_extract(json, '$.expenseId') = ?`, by feedId descending. It also shows only the received items with the same `expenseId` (older servers ignore the filter). The sentences are the same as in the activity list (see "Activity sentences" below).
- Omitting `before` = start from the newest. The group feed uses `seq < before`, the full feed `feedId < before`. `limit` is clamped to 1–100, default 50. Not a number → 400 `VALIDATION`.
- Because of hidden events, `items` can have fewer entries than `limit`, or none, without being the end. **It is the end only when `nextBefore` is null**; otherwise, pass that value as `before` in the next request.
- `feedId`: a global number in the order the server stored the events (the same order as seq within a group). The app sorts its offline cache in this order.
- Every key is always present. Fields that do not apply are `null`, and `changes` is `[]`.
- `createdAt` is **the time the server stored the event** (`events.received_at`). The event's own createdAt (the app clock) is not used, because it disagrees with the list order (seq, feedId) when offline edits are uploaded later or the device clock is wrong. Events stored before this feature existed use their own createdAt. The app draws times and date headers from this value (in the same order as the list). `seq` is the event number within the group (tapping opens the expense of `expenseId`).

Rules for the values:
- `actorMemberId`: the member linked to the event's `actorUserId`. It is looked up in the state **right after** the event is applied; if not found there, in the state after the whole push batch is applied (so the actor of seq 1 `group.created` is the creator added in seq 2). If it is still not found, `null`.
- Expense fields (`description`, `amount`, `currency`) are that expense's values right after the event is applied (`expense_deleted` has the same values as right before the delete). `receipt_*` (phase 7) fills only the `expenseId` and `description` of the expense the receipt is attached to (`attachments[attachmentId].expenseId` in the state right after applying). The `description` of `comment_added` is also the expense description at the time of the comment. Payment fields are also the payment's values right after applying (`status` included).
- `myDelta` (expense kinds, phase 8 `expense_repeated` included; `null` for `recurrence_*`): the change this expense makes to the viewer's balance (the viewer is the caller's member in that group), from the values right after applying: `sign × ((my amount in payers, or 0) − (my share, or 0))`, `sign = refund ? −1 : +1`, in minor units of `currency`. `null` if I am in neither `payers` nor `shares`.
- `changes` (`expense_updated`): every field whose value differs between before and after (because of rule 10, `payers`, `paidBy` and `split` can change even when they are not in `fields`), but only one of the payer fields: if there is one payer both before and after, `payers` is left out (it changed along with an `amount` or `paidBy` edit); if either side has several payers, `paidBy` is left out (it is the main payer derived from `payers`, so a tie or a small amount edit can flip it). Order: `description, amount, currency, fxRateToDefault, paidBy, payers, refund, date, category, shares, split, notes`. `from`/`to` are the values before/after. For `payers`, `shares`, `split` and `notes`, both are `null` (the list shows only the field name), and for `refund` they are booleans. `recurrence_updated` (phase 8) is built from the template before and the template after, each read as an expense (applied like `expense.created`, with any id and date as long as both use the same ones), with the same rules, order and `from`/`to` as `expense_updated` (the template has no `date`). `group_updated` uses the order `name, defaultCurrency, simplifyDebts, defaultSplit`; `simplifyDebts` is a boolean, and `defaultSplit` has both values `null`. A `defaultCurrency` ignored by rule 12 is not a change.
- Hidden (no item is made and no push is sent):
  1. Events with which the applier did not change the state: `created` and `added` with an existing id, `updated` on a deleted expense, `updated` to the same value, `restored` on an expense that is not deleted or was moved (rule 13), `confirmed` on a missing or deleted payment, and so on. Phase 7: `attachment.added` with an existing id or for a missing expense, `attachment.deleted` for a missing or already deleted receipt, `payment.restored` for a payment that is not deleted, is missing or was replaced by an edit (`replaced`). Phase 8: `recurrence.created` with an existing id, `recurrence.updated` and `recurrence.deleted` for a missing or stopped series.
  2. `member.added` at seq 2 (the event in which POST /groups and POST /friends add the creator; it overlaps with `group_created`).
  3. `comment.deleted`.
  4. Unknown types.
  5. A `comment_added` whose comment is deleted **now** (deleting a comment takes its text out of the feed and out of pushes still being held for grouping; a comment written and deleted in the same push is never announced). Only this rule looks at the current state, so it is not in `shared/activity-cases.json` (rules at event time), and a server test checks it.
  6. seq 1 `group.created` of a friend group (phase 6; seq 2 is already hidden by 2). The server records `kind == "friend"` from the state right after the event is applied in `EventMeta.friend` (`false` in older meta; friend groups exist from phase 6), and uses it to decide 6 and `friend_added`. So the validator, `Activity.meta` and the push title all look at one `state.kind` (= `groups.kind`).
  7. `expense_updated` and `recurrence_updated` with empty `changes` (phase 8: an edit that changes only the series mark `recurrenceId` and `occurrence`, which happens when an expense is reattached to a new series because the schedule changed; `changes` does not look at the mark. This also covers a `recurrence.updated` that changes only keys that are not expense fields of the template).
- Inside the push transaction, the server knows the state before and after each event. So it records the values the feed needs (actorMemberId, the before and after values of the target expense or payment, whether the state changed) in the event row's `meta` (server-internal, not in pull), and the feed reads only that. For events stored before this feature existed, the server replays the group log from seq 1 at startup to fill `meta`.

### Activity sentences
The app list and the server push share these sentences. They are built with the viewer as `me` (my member in that group). **Phase 9**: sentences are built per language from the templates in `shared/strings.json` (see "Building sentences" in "Languages and web" above). The app list uses the UI language, and the server push uses the receiver's `users.language`. The table below is the English source, the same as the `en` templates (byte-identical, `shared/activity-cases.json`); other languages are translations with the same placeholders.
- Names: for `me`, `You` at the start of a sentence and `you` elsewhere. If the id is `null` or the name is unknown, `Someone`/`someone`. Otherwise the member's name as is. Phase 9: `words.you`, `words.someone`, and the `self` and `you` templates (see "Building sentences" above).
- Money notation: from phase 9, M(x) per language (see "Money notation M(x)" in "Languages and web" above). English is `€30.00` and `₩15,000` as now, and when the symbol ends in a Latin letter, a U+00A0 goes in: `CHF 12.50`, `ZAR 1,234.56`, `KWD 1,234.567` (in phase 9, KWD, SEK and others were dropped from the symbol table and use ISO codes). No negative numbers (`myDelta` is shown as an absolute value).

Other languages use their own quotation marks and so on (German `„…“`, Japanese `「…」`).

### Push notifications
- When a push in which events were **newly stored** commits (a retry with only duplicate clientIds sends no notification), notifications go to the devices (with FCM tokens) of the group's linked, non-removed members who are **not the sending user**. My own changes are not announced on my devices (same as now). Phase 8: occurrences posted by the scheduler have no sending user, so they go to all linked members (the series' creator included). Unread activity counts them too (`actor_user_id IS DISTINCT FROM`).
- For each receiver, build ActivityItems from this push's new events (`me` = the receiver's member), and drop hidden items and the categories the receiver's notification settings turned off. Categories: `expenses` = `expense_*`, `payment_*` (phase 7 `payment_restored` included), `receipt_*` (phase 7) and `recurrence_*` (phase 8; `expense_repeated` counts as `expense_*`); `comments` = `comment_added` (payment comments included); `members` = `member_*` (`member_left` included), `friend_added` (phase 6) and `group_*` (`group_updated`, phase 10 `group_deleted` and `group_restored`). Phase 10: a deleted group gives no visible notifications except `group_deleted` and `group_restored` (items held for grouping are filtered again at send time), and pushes from an actor the receiver blocked go out as data only (see "Blocking" in "Email and account" above).
- If items are left, a **visible notification** (FCM notification + data): title = the group name (the name at send time; for a friend group (phase 6), the name of the member who is not the receiver's member), body = the sentence if there is 1 item, or the grouped sentence for 2 or more. A visible notification carries the receiver's unread count `total` at that moment as its badge (phase 6, see "Unread activity" below).
- Grouping: per receiver and group, items that come within `EVENSIES_PUSH_BATCH_SECONDS` (default 30) seconds after the last visible notification are not sent right away. They are held, and when that time is up, all held items go out as one visible notification. They are kept only in server memory, so held items are dropped on a restart.
- A push that sends no visible notification (no items left, notifications off, or being grouped) still sends a **data-only message** right away (for sync, same as now).
- The data of a group event notification is always `{"type":"sync","groupId":"...","seq":"<latestSeq at send time>"}` (FCM data values are strings). Phase 6 reminders use `{"type":"remind","fromUserId"}` (see "Reminders" above). When the app gets a sync for an unknown `groupId` (a new friend group), it runs `syncAll()`.
- Phase 8: from the items of a visible notification, first drop a `recurrence_*` item when the same batch has an `expense_*` item with the same `recurrenceId` and **the same `actorMemberId`** (such a pair always comes from one save by one person; if the 30-second batch also has someone else's stop or an Evensies occurrence (no actor), both stay. Creating a recurring expense (`recurrence_created` + `expense_added`), editing the latest occurrence into the future (`expense_updated` + `recurrence_updated`), and deleting and stopping (`expense_deleted` + `recurrence_deleted`) each become one expense sentence. See `batches` in `shared/activity-cases.json`). The feed does not drop them.
- Phase 7: from the items of a visible notification, first drop a `receipt_added` when the same batch has an `expense_added` with the same `expenseId` (saving a new expense with a receipt gives one sentence for that expense. See `batches` in `shared/activity-cases.json`). The feed does not drop them.
- Grouped sentences (2 or more items; the receiver is not the actor, so `You` never appears): if all items have the same `actorMemberId` and all are `expense_added`, `{A} added {n} expenses`; if all are `comment_added`, `{A} added {n} comments`; if all are `expense_repeated` (phase 8, no actor), `{n} repeating expenses were added`; otherwise `{A} made {n} changes`. If the actors are mixed, `{n} new changes` (no actor also counts as one actor).
- App: tapping a visible notification opens that group's activity tab (the friend page for a friend group, `/friends/{fromUserId}` for `remind`). Phase 8: in the activity list, an `expense_repeated` row opens that expense, and a `recurrence_*` row opens the latest occurrence of the series (see "App" in "Recurring expenses" above; nothing happens if there is none). The app's `myDeltaText` is used for `expense_repeated` too. A notification that arrives while the app is in front shows as an in-app banner (same title and body) instead of a system notification, and the app syncs.
- Language (phase 9): the body and grouped sentences are built per receiver in that user's `users.language` (`null`, or a language not in `strings.json`, means English). Held notifications are built in the language at the moment they are sent. The title (the group name, or the other member's name for a friend group) is text a user wrote, so it stays as is. As now, tokens are multicast in groups with the same (title, body, badge), so different languages go out separately.
- Length: a title over 100 characters or a body over 200 (UTF-16) is cut and ends with `…` (that length includes the `…`; surrogate pairs are never split). This keeps long comments, descriptions and group names from going over the FCM/APNs 4096-byte limit and losing the data as well. Sentences in the app list are not cut.
- FCM multicast is sent in chunks of 500 tokens. Device rows are deleted for tokens that FCM answers with `UNREGISTERED`, and for tokens that get `INVALID_ARGUMENT` while other tokens in the same multicast succeed.
- iOS (APNs): visible notifications have `sound: default`, `thread-id: <groupId>` (grouped per group) and, from phase 6, `badge: <total>` (on Android, `notification.notification_count`). Each receiver has a different badge, so `PushNotifier` multicasts to groups of tokens with the same (body, badge). Data-only messages have `content-available: 1`, `apns-priority: 5` and `apns-push-type: background` (the app wakes up in the background and syncs).
- Without FCM credentials (`EVENSIES_FCM_CREDENTIALS_FILE`), pushes are silently skipped.

### Unread activity
Phase 6.

| Method | Path | Request | Response |
|---|---|---|---|
| GET | `/activity/unread` | | `ActivityUnread` |
| POST | `/activity/seen` | `{"feedId": number, "groupId"?: "<uuid>"}` | `ActivityUnread` (after the change) |

```
ActivityUnread {"total": 3, "groups": {"<groupId>": 2, "<groupId>": 1}}
```
- Reference point: `activity_seen.feed_id` per (user, group) (no row = 0). `POST /activity/seen` raises the reference point to `GREATEST(stored value, LEAST(feedId, current max feed_id of events))`, for that group if `groupId` is given (no such group 404; not a current member 403), otherwise for all groups where the caller is a current (not removed) member. It never goes down, and a value that is too large cannot mark future items as read in advance. If `feedId` is not an integer ≥ 0, 400 `VALIDATION`; if `groupId` is not a UUID, 400 `VALIDATION`.
- Unread items = the items built with the same groups, the same `me` and the same hiding rules (hidden case 5 included) as the full feed (`GET /activity`), where (a) `feedId > that group's reference point`, (b) the event's `actorUserId` is not the caller, and (c) the event's `received_at` ≥ the `created_at` of the member row of mine that the feed picked in that group (joining by invite as a new member does not count history from before the join; claiming a placeholder counts history from after the placeholder was created, since that history is about me). `groups` leaves out groups with 0, and `total` = the sum of `groups`.
- Per group, only events after the reference point are read (index `events (group_id, feed_id)`, V7). A user who has read everything costs one index lookup per group.
- `ponytail:` scans at most 500 candidate rows, starting from the newest (beyond that, it undercounts). The app shows `99+` above 99.
- App: the group activity tab badge = `groups[groupId]`, and the full activity button badge = `total`. When the first page of the activity tab or the full activity screen arrives, the app sends `POST /activity/seen` with the largest `feedId` on that page (with `groupId` for a group tab, without it for the full screen; nothing is sent for an empty page). `GET /activity/unread` runs on app start, on return to the foreground and when a push arrives. Online only (no offline queue; on failure the badge stays as it is; a 404 means an older server, so the badge is hidden). The app icon badge is set from the received `total` (iOS: a small platform channel `evensies/badge`, `UNUserNotificationCenter.setBadgeCount`; Android is a no-op, because the launcher shows the notification count). No new dependencies.
- Push badge: only visible notifications for group events carry the receiver's `total` at that moment (see "Push notifications" above). Data-only messages and reminders do not carry it (iOS keeps the current badge for a notification without one).

### Notification settings
| Method | Path | Request | Response |
|---|---|---|---|
| GET | `/me/notifications` | | `NotificationPrefs`. All `true` if never saved |
| PUT | `/me/notifications` | `NotificationPrefs` (`expenses`, `comments` and `members` are required booleans, replaced as a whole. `reminders` (phase 6) is optional: if missing, the stored value stays; if present, a boolean) | `NotificationPrefs` (all four keys). 400 `VALIDATION` if a required key is missing or not a boolean, or if `reminders` is not a boolean (`null` included) |

```
NotificationPrefs {"expenses": bool, "comments": bool, "members": bool, "reminders": bool, "emailDigest": string, "emailDigestEffective": string}
```
`expenses` = expenses and payments, `comments` = comments, `members` = members joining, being added, being removed or leaving, and group setting changes (name, currency, simplify debts, default split). `reminders` (phase 6) = visible notifications for reminders other people send (`true` if never saved). Phase 2–5 apps do not send `reminders`, so they never change its value. Even with these off, the data messages for sync keep coming. `DELETE /me` deletes the settings too. `emailDigest` and `emailDigestEffective` (phase 10): see "Summary emails" in "Email and account".

Building an app for another server (phase 11): the Evensies app from the stores talks only to the official server. To use another server, build an app with a different name, icon and bundle ID (`TRADEMARKS.md`) with `--dart-define=EVENSIES_SERVER_URL=https://<server>`, and set the server's `EVENSIES_APPLE_CLIENT_ID` (the new bundle ID) and `EVENSIES_GOOGLE_CLIENT_IDS`, the app's `EVENSIES_GOOGLE_SERVER_CLIENT_ID`, and the Firebase files to your own.
